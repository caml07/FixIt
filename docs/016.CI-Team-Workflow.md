## Alcance de implementación del usuario: Chat + React

Este es el trabajo propio de `caml07`; no implica asumir Auth ni Tickets.

### `services/chat`

- Express + Socket.IO y MongoDB/Mongoose para mensajes persistentes.
- `GET /api/v1/tickets/{ticketId}/messages` con cursor, límite y orden cronológico del contrato.
- `ticket:join`, `ticket:leave` y `chat:send`; ACK después de persistir, idempotencia por `clientMessageId` y deduplicación del cliente por `Message.id`.
- Validar la sesión con Auth y consultar a Tickets para cada lectura, join, envío y audiencia de broadcasts. No confiar en roles, sender IDs, rooms ni eventos NATS como autorización.
- Rate limits contractuales, errores tipados, reconexión/historial y pruebas negativas de acceso/reasignación.
- Consumidor JetStream para cambios de Tickets, inbox idempotente y reconstrucción de la proyección. Los eventos ayudan a sincronizar; Tickets sigue siendo la autoridad.
- Desarrollar primero con adaptadores/simuladores locales y usuarios sintéticos conformes a los contratos de Auth/Tickets. Después integrar las implementaciones reales de Rina/Valeria.

### `apps/web`

- Una SPA React para Reporter, Support Agent y Admin; inglés, responsive y dirección visual B (*Campus / Warm*).
- Shell y navegación por rol; integrar login, sesión y cambio inicial de contraseña a través de Auth, sin implementar su servicio.
- Reporter: My Requests, New Request y Ticket Detail; formulario con urgencia y evidencia según 0.2.0.
- Support Agent: Support Inbox con Available / Assigned to me, claim, trabajo y resolución.
- Admin: All Tickets y User Management mediante las rutas de Auth/Tickets.
- Ticket Detail: Conversation, Activity y Details separados; Chat se habilita según estado, reconcilia historial al reconectar y deduplica mensajes.
- La UI refleja permisos y errores, pero el backend decide ownership, autorización y estado. No implementar un segundo sistema de permisos en React.

No empezar por notificaciones históricas, chat global, un cuarto servicio, microfrontend, gateway, service mesh ni un sistema de archivos separado.

## Ramas y alcance

- `dev`: documentación, OpenAPI y migraciones **contract-first**; no código ejecutable hasta que el equipo acuerde otra política.
- `prototype/auth-g4`: prototipo existente con Express/Prisma, **no** Auth del MVP integrado, reutilizar después de review.
- feat/chat y feat/ui parten de dev actualizado; no fusionar features hasta que Auth/Tickets y bases definitivas estén disponibles. feat/auth se conserva sin cambios.
- PR pequeño por contrato/feature, usando [plantilla compartida](../.github/pull_request_template.md); un reviewer **diferente del autor**. Ninguna IA hace commit, push, merge, provisionamiento o cambio de secretos sin instrucción humana explícita.
- No editar el área de otra persona sin coordinar. `docs/openapi.json` y migraciones SQL tienen **owner coordinado**; un PR modifica el contrato compartido antes de producir controlador. Cambios simultáneos a esos dos archivos deben serializarse.
- **Gate de Mr Félix:** la baseline 0.2.0 (OpenAPI + 3NF/FK/migraciones) está validada y commiteada en `dev`; la revisión técnica del equipo sigue pendiente. Los controladores deben conservar ese commit como ancestro. El contrato incluye urgencia/prioridad y evidencia multimedia.

## CI inicial realmente implementada

`.github/workflows/ci.yml` ejecuta en PR y push a `dev`/`main` con `contents: read`:
1. `node scripts/ci/check-docs.mjs`: verifica enlaces relativos de Markdown y archivos esenciales.
2. `node scripts/ci/check-contract.mjs`: verifica sintaxis JSON, operaciones, componentes/referencias. `npx --yes @redocly/cli@2.79.0 lint docs/openapi.json` añade **validación formal de OpenAPI** (reporta 5 advertencias existentes; no equivalen a error). Urgencia, prioridad y evidencia multimedia están sincronizadas en la baseline 0.2.0.
3. `node scripts/ci/check-apps.mjs`: descubre paquetes en `services/*` y `apps/*`. `services/chat` ya tiene `package.json`, lockfile y scripts `lint`, `typecheck`, `test`, `build`; `apps/web` se incorporará con la misma convención. CI ejecuta `npm ci`, los scripts y `npm audit --omit=dev --audit-level=high`. Si falta un script, CI falla.
4. `sh scripts/ci/check-migration.sh`: inicia un PostgreSQL 17 **efímero y aislado de la red** para aplicar el DDL y verificar tablas, FKs y categorías semilla. Ejecuta un contenedor de prueba, **no toca RDS/Atlas**.

Una CI verde al principio significa **checks documentales + Redocly + DDL smoke pass**, **NO** G1/G3/G4/G5 PASS. La baseline 0.2.0 también pasó `prisma validate`, smoke SQL, `prisma migrate deploy/status` y `prisma migrate diff` en PostgreSQL 17 desechable. La revisión del equipo y los tests de negocio sobre servicios reales siguen pendientes; el commit previo a controladores ya está registrado. `services/chat` ya tiene paquete y pruebas locales; `apps/web` aún no existe. No atribuir pruebas exitosas a módulos sin paquete.

## CI al incorporarse los paquetes de los servicios

**Actualizacion en el worktree de Auth:** el checker admite tanto el paquete
raiz existente de Auth como paquetes independientes bajo `services/*` y
`apps/*`. Cada paquete descubierto exige lockfile, lint, typecheck, test y
build. En Auth, `npm test` crea PostgreSQL 17 desechable en loopback, aplica
Prisma Migrate, usa un rol SQL limitado y limpia el contenedor. El lint raiz
comprueba TypeScript (incluidos parametros y locales sin uso) y sintaxis del
checker; no sustituye un futuro ESLint de proyecto. Ver el [runbook Auth](../services/auth/README.md).
Esta adaptacion no decide la estructura definitiva de los demas servicios.

**Convención de carpetas para esta CI:** `services/auth/`, `services/tickets/`, `services/chat/`, `apps/web/`. Chat ya sigue esta convención; cada paquete requiere `package.json`, `package-lock.json` y los cuatro scripts descritos. Si se elige monorepo/gestor distinto, **modificar CI y su documentación en el mismo PR** antes de meter código. No generar carpetas vacías en la rama documental.

Por cada módulo React/Node: `npm ci` con lockfile, lint, format-check, typecheck, test unitario, test integración y build; un job por módulo modificado. Después:
- PostgreSQL y Mongo efímeros + NATS JetStream en runners para probar repositorios, mensajes y eventos; sin credenciales Cloud.
- Contratos entre Auth/Tickets/Chat: tests HTTP y Socket.IO con respuestas negativas (403/404/409/422/503) e inyección; no solo happy path.
- Tests cruciales: login/logout/expiración, BOLA, claim simultáneo (una sola asignación), outbox/JetStream duplicados/recovery, no ACK si Mongo cae, revocación de salas Socket.IO y diferencia entre **urgencia propuesta** y **prioridad oficial**.
- Dependencias: RFC antes de agregar paquete backend, `npm audit` con reporte y justificación de alertas; secretos excluidos de logs y artefactos.
- La UI debe testear carga/error/vacío, teclado y móvil; tests visuales al tener aplicación funcional.
- **No se integra un job de deploy automático**. Cloud y presupuesto se revisan como cambio separado con autorización previa.

## Ruta mínima de Cam Route por tarea

| Petición a la IA | Ruta | Evidencia que debe dejar |
| --- | --- | --- |
| Cambio en OpenAPI/Prisma/DDL | `cam-route → doc-system + fixit-contract-first` | diff de contrato, validadores, verificación SQL, revisión y commit de contrato anterior a controllers |
| Implementar módulo Node/Express | `cam-route → ai-native-workflow + tdd` | tests con casos negativos, lint/typecheck, CI y revisión de permisos |
| React + Chat/Socket.IO | `cam-route → ai-native-workflow + (impeccable si trabajo UI)` | mockups/estados solo si proceden; prueba real de mensajes y permisos. En React se respeta `no-use-effect` |
| Comprobar PR y levantar CI | `cam-route → fixit-ci-handoff` | comandos y salidas reales; nunca declarar green un test inexistente |
| Infraestructura híbrida | `cam-route → doc-system` y [015](015.Hybrid-Development.md) | red/egreso/TLS, riesgos, costo bruto y no despliegue sin permiso |

**Recomendación de Cam Route:** cuando el MVP tenga un flujo ejecutable, crear **una sola skill de proyecto `verify` con `create-verification-skill`**: conducir login → ticket → claim → mensaje → cierre con datos ficticios. Antes de eso, la skill no puede demostrar resultados y no debe fabricarse como si fuera ejecutable. Después, usar `code-review` para PRs y `security-audit` en Auth/Chat; evitar un "thermo review" en cada cambio mínimo.

## Definition of Done de un PR

- [ ] Requisito FR/NFR, endpoints, migraciones y ámbito de archivos referenciados.
- [ ] Contrato y migración en un commit **anterior** si cambia API/DB; revisión coordinada.
- [ ] Pruebas de comportamiento y **al menos un caso negativo** por recurso protegido.
- [ ] `npm ci`, lint/typecheck/tests/build del módulo pertinente cuando existan, más checks de contratos/docs.
- [ ] Sin credenciales ni variables reales, `npm audit`/Dependency RFC donde corresponda.
- [ ] Resumen de comprobaciones **ejecutadas**, pendientes y riesgos; revisión por otra persona.
- [ ] Nada de auto-merge, auto-push ni deploy por agentes.
