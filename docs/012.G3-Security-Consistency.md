# 012 · G3 — Security & Consistency (revision inicial)

**Alcance:** contrato de FixIt [G1](010.G1-Contracts.md), invariantes y pruebas [Delivery](005.Delivery.md). Se ha validado solo un **spike desechable** en `spikes/g2`; no existe aun implementacion de producto. **G3 NO PASS.** Las pruebas prolongadas y el presupuesto AWS de G2 quedan expresamente **postergados**, no aprobados.

## Evidencia ejecutada (10 nov 2026)

Ruta: `cam-route` → `ai-native-workflow` (Deep, seguridad/consistencia) + `security-audit` (guia focalizada).

**Superficies de prueba:** HTTP de Auth/Tickets/Chat y eventos Socket.IO a traves de Caddy en `127.0.0.1`, con PostgreSQL, MongoDB y NATS reales y credenciales ficticias; Podman rootless aislado.

**Hallazgo G3-01 — ALTO, corregido solamente en el spike: fuga al socket con sesion revocada.**

- **Origen:** `spikes/g2/src/server.mjs` aceptaba una sesion en el handshake Socket.IO, pero al enviar `chat:message` usaba solo `socket.data.user` (capturado al conectar) y la audiencia actual del ticket. El token revocado podia continuar **recibiendo** mensajes: un fallo de confidencialidad, aunque `chat:send` ya comprobaba permiso.
- **Reproduccion negativa:** `spikes/g2/g3-security.mjs` crea un ticket, conecta Reporter+Agent+tercero, revoca el token del Reporter por `POST /api/auth/logout`, y envia desde el Agent. El test fallo por **recibir 2 mensajes cuando solo debia recibir el anterior al logout**. Tambien se agrego logout real al spike; antes el test habia descubierto que faltaba ese endpoint.
- **Mitigacion:** antes de cada broadcast, Chat filtra por membresia de sala y audiencia actual y vuelve a llamar a Tickets/Auth para comprobar **sesion vigente y permiso de lectura de cada destinatario**. Ante rechazo o timeout no se envia el cuerpo; se quita la sala. La verificacion por destinatario introduce llamadas adicionales, por lo que G2 debe medir esta version antes de estimar costo/latencia. **No copiar literalmente esta implementacion de spike sin revisar escalabilidad y error handling.**
- **Verificacion verde:** ambas topologias pasaron **7/7 checks G3**; archivos de evidencia:
  - `../spikes/g2/results/g3/g2-three-shared2-native-c11-20261111T051524Z.json`
  - `../spikes/g2/results/g3/g2-two-shared2-native-c11-20261111T051633Z.json`
- **Estado:** **FIXED IN SPIKE ONLY**. El cambio debe implementarse y volverse a probar en el producto G4. No declararlo resuelto para produccion.

## Decisiones recomendadas para el MVP (todavia propuestas)

**Sesion:** Auth es unica autoridad; token opaco con hash en DB, revocacion inmediata en introspeccion interna. Todo socket debe autorizarse al conectar y para `ticket:join`, `chat:send` y **cada broadcast privado**. El estado de un room solo ayuda a enrutar, no es un permiso. No introducir cache de autorización hasta contar con invalidacion real probada.

**Tickets:** las transiciones y claim son de PostgreSQL; usar `UPDATE ... WHERE`/version y auditoria/outbox en la misma transaccion. Respuesta 409 al perdedor, sin emitir evento de exito. Reasignacion cambia audiencia; los mensajes iniciados mientras el agente estaba autorizado pueden terminar si su operación se solapo con la reasignación (politica MVP por validar con equipo, no garantia atomica entre bases).

**Eventos:** NATS JetStream es at-least-once; consumidor idempotente por `eventId`, mantener version de agregado y reconciliar gaps. No usar mensajes/eventos para decidir ownership. No contar **outbox drenada** como evidencia de consumo exactamente una vez.

## Salida verificable antes de aprobar G3

El futuro código de `services/` debe superar la suite negativa desde API y WebSocket reales, CSRF/Origin/secure-cookie, rate limit, periodo de activacion, competencia de claim y race de reasignacion, reboot con estado persistente y duplicados/out-of-order de JetStream. Documentar responsables y logs sin secretos. La aceptacion de ADR-005 y despliegue AWS siguen pendientes de revision externa.
