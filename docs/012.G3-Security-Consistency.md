## Evidencia ejecutada (10 nov 2026)

Ruta: `cam-route` → `ai-native-workflow` (Deep, seguridad/consistencia) + `security-audit` (guia focalizada).

**Superficies de prueba:** HTTP de Auth/Tickets/Chat y eventos Socket.IO a traves de Caddy en `127.0.0.1`, con PostgreSQL, MongoDB y NATS reales y credenciales ficticias; Podman rootless aislado.

**Hallazgo G3-01 — ALTO, corregido solamente en el spike historico: fuga al socket con sesion revocada.**

- **Origen:** el servidor experimental (historico en Git `5df9b8c`) aceptaba una sesion en el handshake Socket.IO, pero al enviar `chat:message` usaba solo `socket.data.user` (capturado al conectar) y la audiencia actual del ticket. El token revocado podia continuar **recibiendo** mensajes: un fallo de confidencialidad, aunque `chat:send` ya comprobaba permiso.
- **Reproduccion negativa:** la suite historica creaba un ticket, conectaba Reporter+Agent+tercero, revocaba el token del Reporter por `POST /api/auth/logout`, y enviaba desde el Agent. El test fallo por **recibir 2 mensajes cuando solo debia recibir el anterior al logout**. Tambien se agrego logout real al spike; antes el test habia descubierto que faltaba ese endpoint.
- **Mitigacion:** antes de cada broadcast, Chat filtra por membresia de sala y audiencia actual y vuelve a llamar a Tickets/Auth para comprobar **sesion vigente y permiso de lectura de cada destinatario**. Ante rechazo o timeout no se envia el cuerpo; se quita la sala. La verificacion por destinatario introduce llamadas adicionales, por lo que G2 debe medir esta version antes de estimar costo/latencia. **No copiar literalmente esta implementacion de spike sin revisar escalabilidad y error handling.**
- **Verificacion verde:** ambas topologias pasaron **7/7 checks G3**, con resultados y limites consolidados en [013.Spike-Results](013.Spike-Results.md). Los archivos de evidencia crudos se retiraron a peticion del usuario; se recuperan desde Git si fueran necesarios.
- **Estado:** **FIXED IN SPIKE ONLY**. El cambio debe implementarse y volverse a probar en el producto G4. No declararlo resuelto para produccion.

## Decisiones recomendadas para el MVP (todavia propuestas)

**Sesion:** Auth es unica autoridad; token opaco con hash en DB, revocacion inmediata en introspeccion interna. Todo socket debe autorizarse al conectar y para `ticket:join`, `chat:send` y **cada broadcast privado**. El estado de un room solo ayuda a enrutar, no es un permiso. No introducir cache de autorización hasta contar con invalidacion real probada.

**Nota de clases (NO confirmada por escrito):** el usuario recuerda almacenar sesiones/tokens en MongoDB/Mongoose y marcar documentos `deprecated`. No reinterpretar esto como permiso de conservar una sesion autenticable despues del logout; confirmar con Felix si se referia a estado historico, expiracion o rotacion. El PDF exige Session/JWT seguros, no determina la base de almacenamiento. [G1](010.G1-Contracts.md) conserva esta pregunta.

**Tickets:** las transiciones y claim son de PostgreSQL; usar `UPDATE ... WHERE`/version y auditoria/outbox en la misma transaccion. Respuesta 409 al perdedor, sin emitir evento de exito. Reasignacion cambia audiencia; los mensajes iniciados mientras el agente estaba autorizado pueden terminar si su operación se solapo con la reasignación (**alternativa A seleccionada por el usuario el 11 nov**, pendiente de ratificacion del equipo y pruebas).

**Eventos:** NATS JetStream es at-least-once; consumidor idempotente por `eventId`, mantener version de agregado y reconciliar gaps. No usar mensajes/eventos para decidir ownership. No contar **outbox drenada** como evidencia de consumo exactamente una vez.

### Paquete de decision G3 para revision del equipo (11 nov; B2 A SELECCIONADA, G3 NO PASS)

**Objetivo:** adoptar un conjunto coherente de garantias de seguridad para el
MVP, sin crear microgates ni mas endpoints, y sin declarar el diseño probado.
La mayor decision de producto es la politica de operaciones en vuelo (B2).

| Dimension | Direccion recomendada para el MVP | Alternativa/costo | Prueba de aceptacion futura |
| --- | --- | --- | --- |
| **Navegador, sesiones y Socket.IO** | Servir frontend y API desde **mismo origin HTTPS/WSS**; cookie opaca `__Host-` con `HttpOnly; Secure; SameSite=Strict`. Usar token CSRF **ligado a sesion** para mutaciones autenticadas, validar `Origin` y `Sec-Fetch-Site` (con fallback), restringir CORS a origin explicito y usar `allowRequest` para validar Origin en WebSocket | Multiples origins/clients nativos requieren politica diferente; SameSite por si solo no basta | Origin malicioso, CSRF ausente/falso, socket ajeno y cookie insegura son rechazados en tests HTTPS; login/bootstrap reciben proteccion contra login-CSRF |
| **BOLA/IDOR + revocacion** | **Tickets** decide ownership y estado desde backend; filtros de consulta por actor y recurso, no solo UI. Chat verifica sesion+permiso de **cada receptor** antes de broadcasts; invalidacion y fallos son **fail-closed** | Revalidacion sin cache cuesta hops; cache autorizativa prematura introduce riesgo de revocacion obsoleta | Tests con Reporter ajeno, agente anterior y socket que hizo logout; respuestas sin filtracion de existencia |
| **B2: envio simultaneo a reasignacion** | **SELECCIONADA POR EL USUARIO (A, 11 nov):** nuevas operaciones del agente anterior tras commit se rechazan; las ya autorizadas y en vuelo pueden finalizar, auditadas; no emitir a agente anterior tras perder acceso y no afirmar serializacion PG/Mongo | Barrera estricta exigiría coordinacion/compensacion entre PG y Mongo y mayor complejidad | Intercalar envio y reasignacion artificialmente antes/despues de la comprobacion; documentar las garantias que realmente se ofrezcan |

## Salida verificable antes de aprobar G3

El futuro código de `services/` debe superar la suite negativa desde API y WebSocket reales, CSRF/Origin/secure-cookie, rate limit, periodo de activacion, competencia de claim y race de reasignacion, reboot con estado persistente y duplicados/out-of-order de JetStream. Documentar responsables y logs sin secretos. La aceptacion de ADR-005 y despliegue AWS siguen pendientes de revision externa.

**Nueva rubrica (11 nov):** el reporte de seguridad G3 debe incluir **pruebas adversariales reales, exploit logs, medidas correctivas y re-test** sobre la API del producto, no solo el spike, para cubrir BOLA/IDOR, inyeccion SQL/NoSQL, CORS con credenciales y bypass de rate-limit. **Antes de escribir nuevos controladores**, revisar/commitear `docs/openapi.json` y el modelo/migraciones 3NF conforme al [documento academico](references/COP3851_Capstone_2026-11-11.md). Preparar tambien una defensa en vivo donde el equipo pueda explicar y extender middleware de autorizacion.

**Continuidad:** la suite historica no se conserva ejecutable en el checkout actual. En G4 implementar **tests negativos nuevos** contra los contratos de la API real, incluyendo logout con socket previamente conectado, acceso por recurso, reasignacion y mensajes salientes. El historial del codigo experimental sigue disponible en Git (commit `5df9b8c`), pero **no lo usar como backend final**. **No hay commits ni push sin orden del usuario.**
