# 002 · Requirements — FR / NFR

Los requisitos de este documento son **objetivos propuestos**, no funcionalidades verificadas. Formato: ID estable, prioridad **Must / Should / Could** y criterio de aceptación comprobable. Los criterios con tiempo/volumen son metas de prueba para el equipo y podrán ajustarse con evidencia. La [especificacion COP3851 del 11 nov](references/COP3851_Capstone_2026-11-11.md) agrega requisitos academicos **obligatorios para el proceso**: OpenAPI/esquema 3NF con FK en commit **anterior** a generar controllers con IA, `CLAUDE.md` o `GEMINI.md`, Dependency RFC y auditoria adversarial. Seguimiento sin crear otro gate: [011.Gates](011.Gates.md).

## Funcionales (FR)

| ID | Prioridad | Requisito único | Evidencia/aceptación prevista |
| --- | --- | --- | --- |
| FR-001 | Must | El sistema autentica a un usuario autorizado y cierra su sesión. | Una sesión caducada/revocada no puede invocar API ni Socket.io; logout invalida la sesión activa. |
| FR-002 | Must | El sistema aplica Reporter, Support Agent y Admin con autorización por recurso. | Reporter ajeno recibe 403/404 consistente al consultar/modificar ticket de otro; pruebas negativas por rol. |
| FR-003 | Must | Reporter crea un ticket IT con título, descripción y categoría válida; salon/equipo son opcionales. | Devuelve 201, dueño autenticado y estado OPEN sin agente, con o sin ubicacion; input inválido produce 400/422 documentado. |

| FR-005 | Must | Un agente reclama un ticket OPEN sin responsable mediante operación atómica. | Dos agentes simultáneos: una asignación y un 409, sin duplicidad en base. |
| FR-006 | Must | Agente asignado cambia ASSIGNED → IN_PROGRESS → RESOLVED de forma autorizada. | Cambios inválidos o actor no autorizado se rechazan y no escriben evento. |
| FR-007 | Must | Reporter confirma cierre de ticket RESOLVED propio; Admin puede cerrar por excepción. | Se guarda CLOSED con actor/fecha; chat queda solo lectura. |
| FR-008 | Must | Reporter cancela su ticket aún OPEN sin agente. | CLOSED/CANCELLED no aceptan nuevos mensajes ni reclamo. |
| FR-009 | Must | Cada ticket asignado tiene conversación persistente entre reporter, agente asignado y Admin. | Recargar sesión recupera mensajes ordenados; tercero no puede leer ni escribir. |
| FR-010 | Must | Un mensaje validado se guarda antes de notificarse por Socket.io. | ACK solo después de persistir; fallo Mongo devuelve error, sin mensaje fantasma. |
| FR-011 | Must | Admin puede reasignar un ticket y dejar evento auditado. | Agente anterior pierde acceso a escribir/leer futuros mensajes después de reasignación; prueba de sala socket. |
| FR-012 | Must | El sistema conserva evento de cada creación, toma, cambio de estado, reasignación y cierre. | Timeline contiene actor, fecha, transición y ticket. |

| FR-014 | Must | Se puede desplegar una versión trazable de FixIt en AWS y demostrar S3 según el criterio que confirme Marvin. | Demostración del deploy por commit SHA, objeto/version S3 **si se exige versioning**, o website estático **si se exige hosting**, y evidencia de rollback cuando aplique; alcance de S3 pendiente de confirmar. |
| FR-015 | Should | Administrador visualiza resumen de cantidad de tickets por estado. | Conteo obtenido de fuente relacional, no supuesto en frontend. |
| FR-016 | Must | Reporter puede adjuntar una fotografía **opcional** como evidencia de un ticket IT, sin que el archivo sea necesario para reportar. | Criterio MVP propuesto: una foto JPG/PNG/WebP de hasta 5 MB, revisando contenido real, no solo extensión; rechazar archivos inválidos y permitir ticket sin fotografía. Toda lectura/descarga exige autorización por ticket; almacenar fuera de rutas web públicas y excluir datos sensibles de logs. El backend de almacenamiento se define al implementar, sin obligar a S3. |

Tras desconexión, el cliente consulta el estado actual y el historial permitido; no se prometen push, email, bandeja histórica de notificaciones ni delivery garantizado por socket. |

## No funcionales (NFR)

| ID | Prioridad | Requisito / objetivo medible propuesto | Cómo medir o verificar |
| --- | --- | --- | --- |
| NFR-001 | Must | Todas las operaciones protegidas validan identidad, rol y ownership en backend (HTTP y sockets). | Matriz negativa automatizada; nunca confiar en `userId` enviado como dueño. |
| NFR-002 | Must | Solo el proxy web expone tráfico público; PostgreSQL (5432), MongoDB (27017) y puerto interno API no se publican a Internet. | Revisión Docker bindings + SG + prueba externa; SSM solo con rol autorizado. |
| NFR-003 | Must | TLS para acceso público y cookies `HttpOnly; Secure; SameSite=Strict` como exige COP3851; CSRF, `Origin` permitido, CORS sin `*` y cabeceras de seguridad. | Inspección bajo HTTPS/WSS, Set-Cookie, pruebas cross-site y Origin inválido (también WebSocket); no contar HTTP del spike como prueba. |

| NFR-006 | Must | Los mensajes aceptados sobreviven a reinicio de API y reconexión de socket. | Enviar, reiniciar API, cargar historial desde Mongo. |
| NFR-007 | Must | Existe procedimiento probado de restauración de datos de desarrollo/demo. | Export + restore en entorno desechable; registrar duración real, no prometer RPO/RTO no medidos. |
| NFR-008 | Must | Costos AWS observables con alertas y retención de artefactos/versiones definida; ninguna suscripción de pago sin aprobación. | Cost & Usage, presupuesto, lifecycle y permisos de cuenta revisados. |
| NFR-009 | Must | La app arranca localmente con pasos reproducibles y sin depender de credenciales AWS. | Seguir README de setup en máquina limpia usando datos ficticios. |
| NFR-010 | Should | Las rutas frecuentes responden en p95 ≤ 1 s y mensajes visibles en p95 ≤ 2 s bajo 10 usuarios de prueba. | Ensayo repetible con red y carga delimitadas; si falla, registrar resultado real. |
| NFR-011 | Should | Interfaz usable en móvil y escritorio, con navegación por teclado, labels y contraste razonable. | Evaluación manual en 360px y 1280px, keyboard-only y contraste. |
| NFR-012 | Must | Logs sin contraseñas, tokens, contenido sensible de mensajes ni secretos; trazabilidad de errores. | Revisión de logs ante login fallido, claim, websocket y fallo DB. |
| NFR-013 | Must | Cuando el storage Mongo está caído, el sistema no confirma mensajes como enviados. | Test de falla controlada y recuperación posterior. |

## Política de permisos propuesta

| Acción | Reporter | Support Agent | Admin |
| --- | --- | --- | --- |
| Crear ticket | Sí | Sí* | Sí* |
| Ver ticket completo | Propios | Asignados | Todos |
| Ver lista de disponibles | No | Resumen sin mensajes sensibles | Sí |
| Reclamar ticket OPEN | No | Sí | Por definir |
| Chat en ticket | Propios asignados y activos | Asignados y activos | Todos activos |
| Resolver ticket | No | Asignados | Sí |
| Cerrar RESOLVED | Dueño | No | Sí |
| Cancelar OPEN | Dueño | No | Sí |
| Reasignar | No | No | Sí |
| Gestión de usuarios | No | No | Sí |

*Crear tickets como Agent/Admin es una comodidad prevista, no una necesidad del demo. Cierre, re-asignación, datos sensibles y estados anómalos se prueban de lado del servidor. Los tickets no asignados exponen solo campos adecuados para la cola, no el chat privado.

## Reglas de dominio que no se deben romper

- Estado inicial OPEN y `assigneeId = NULL`.
- Claim válido solo si `status=OPEN` y `assigneeId=NULL`, con update condicionado en DB.
- No duplicar IDs de mensajes en reintentos; cada envío lleva `clientMessageId` y restricción de unicidad por ticket/emisor.
- PostgreSQL guarda ticket/estado/auditoría crítica; MongoDB guarda mensajes. No asumir transacciones atómicas entre ambos motores.
- Socket.io nunca autoriza solo por pertenecer a la sala: validar también ante envío y cambios de asignación.
- Fotos y sus metadatos se vinculan al ticket; no son claims de sesion ni se guardan en tokens. Controlar tamaño, tipo real de archivo, acceso y privacidad (incluidos metadatos de imagen), y evitar URLs publicas sin control.
- Distinguir 401 (sin sesión), 403 (prohibido), 404 (no encontrado o no revelable), 409 (competencia/estado incompatible) y 422 (validación), documentados en OpenAPI.

## Pendientes que requieren decisión

1. **Resuelto para el diseño:** sesión opaca en Auth/PostgreSQL (seleccionada por usuario, equipo pendiente), no JWT por inercia. Ver [006.Decisions](006.Decisions.md). Queda pendiente el hashing compatible con NIST y timeouts exactos.
2. ¿Se permite que un reporter escriba antes de asignación? Propuesta actual: **no**, pero el ticket sí conserva su descripción.
3. ¿Un agente puede escribir en ASSIGNED o solo tras IN_PROGRESS? Propuesta: ambos; mensajes se bloquean después de RESOLVED.
4. ¿Recuperación de contraseña y registro libre? Quedan fuera del MVP salvo que rúbrica los exija.
5. ¿Reabrir RESOLVED? No para el primer demo. ¿Cierre por Admin sin confirmación? Solo con motivo auditado.
6. Metas de p95 y retención de datos deben recalibrarse al medir en infraestructura real.
