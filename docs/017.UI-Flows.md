# 017 · FixIt UI/UX flows

## Propósito y alcance

Este documento convierte el brief de UI aprobado en flujos navegables para diseño, prototipado y posterior implementación. Los diagramas describen el comportamiento esperado de la interfaz; **no certifican que los endpoints o servicios estén implementados**.

- Producto: FixIt, IT Help Desk single-tenant para el piloto académico de Keiser University LAC.
- Roles: Reporter, Support Agent y Admin.
- Plataforma: web responsive; desktop y mobile tienen la misma prioridad.
- Idioma visible: inglés. La documentación y las notas de diseño se mantienen en español.
- Los nombres de pantallas, tabs, botones y estados visibles se escriben en inglés para coincidir con la UI.

## 1. Entrada a la aplicación y navegación por rol

Todos los roles utilizan el mismo shell. Después de autenticar, la aplicación presenta únicamente los destinos permitidos para el rol. No existe registro público.

~~~mermaid
flowchart TD
    A([Abrir FixIt]) --> B[Sign in]
    B --> C{Credenciales válidas?}
    C -- No --> D[Mostrar error de acceso o rate limit]
    D --> B
    C -- Sí --> E{mustChangePassword?}
    E -- Sí --> F[Password change-only]
    F --> G[Change temporary password]
    G --> H{Activación aceptada?}
    H -- No --> I[Mostrar errores o credencial temporal vencida]
    I --> G
    H -- Sí --> J[Revocar sesión provisional]
    J --> B
    E -- No --> K[Sesión FULL]
    K --> L{Rol autenticado}
    L -- REPORTER --> M[My Requests]
    L -- SUPPORT_AGENT --> N[Support Inbox]
    L -- ADMIN --> O[Admin Workspace]
    O --> P[All Tickets]
    O --> R[User Management]
    M --> Q[Acciones de cuenta y Logout]
    N --> Q
    P --> Q
    R --> Q
~~~

**Reglas UX y seguridad**

- La sesión restringida de cambio de contraseña no permite acceder a Tickets ni Chat.
- Después de activar la contraseña temporal, el usuario vuelve a iniciar sesión para obtener una sesión FULL.
- Una sesión expirada, revocada o no válida devuelve al flujo de Sign in; la UI no debe conservar acciones protegidas habilitadas.
- Admin crea cuentas personales con rol Reporter o Support Agent. No hay registro público ni creación de otro Admin desde la UI.
- Ocultar una opción en la navegación mejora la experiencia, pero la autorización real siempre pertenece al backend.

## 2. Reporter · Crear y seguir una solicitud

El formulario mantiene visibles únicamente los datos esenciales. Location y Equipment son opcionales y permanecen dentro de **Additional details (optional)** hasta que el usuario decida expandirlos.

~~~mermaid
flowchart TD
    A[My Requests] --> B[New Request]
    B --> C[Completar Subject, Category y Description]
    C --> D{Necesita datos adicionales?}
    D -- No --> G[Revisar formulario]
    D -- Sí --> E[Expandir Additional details]
    E --> F[Completar Location y/o Equipment]
    F --> G
    G --> H[Submit request]
    H --> I{Validación aceptada?}
    I -- No --> J[Mostrar errores junto a los campos]
    J --> C
    I -- Sí --> K[Servidor crea ticket y asigna createdAt]
    K --> L[Ticket OPEN, sin assignee]
    L --> M[Confirmación de creación]
    M --> N[My Requests / Ticket detail]
    N --> O{Estado actual}
    O -- OPEN --> P[Consultar estado o cancelar solicitud propia]
    P -->|Cancelar| Q[CANCELLED]
    P -->|Esperar asignación| N
    O -- ASSIGNED --> R[Ver detalles y conversación habilitada]
    O -- IN_PROGRESS --> R
    O -- RESOLVED --> S[Revisar resolución]
    S --> T[Close ticket]
    T --> U[CLOSED]
    O -- CLOSED --> V[Consultar historial]
    O -- CANCELLED --> V
~~~

**Comportamiento del formulario**

- Campos principales: **Subject**, **Category**, **Description** y **Urgency** (`Low`, `Normal`, `High`).
- **Category** se carga desde el catálogo de categorías IT existente; no se crea una taxonomía nueva en la UI.
- **Additional details (optional)** contiene **Location** y **Equipment**. Su estado inicial es colapsado.
- La hora de creación la genera el servidor. La UI no envía ni permite editar createdAt.
- Después de crear, el ticket comienza en OPEN y sin agente asignado.
- El Reporter puede cancelar su propio ticket mientras esté OPEN; no se presenta Cancel como acción general para otros estados.
- Cuando el ticket pasa a RESOLVED, el Reporter puede revisar el resultado y cerrarlo.

**Dependencias de contrato — no simular como implementadas**

- La creación requiere `title`, `description`, `category` y `reporterUrgency`; Subject se mapea a title. `createdAt` es generado por servidor.
- El Reporter puede adjuntar evidencia opcional después de crear el ticket mientras siga `OPEN`: máximo 5 archivos/2 videos, imagen hasta 5 MiB, MP4 hasta 25 MiB, 50 MiB total por ticket. Una subida por petición; la ausencia de archivos no bloquea la creación.
- La urgencia propuesta por Reporter (`LOW/NORMAL/HIGH`) es distinta de la prioridad oficial (`P1_CRITICAL/P2_HIGH/P3_NORMAL/P4_LOW`). Esta última inicia `null`, solo la establece el Agent asignado/Admin y debe existir antes de `IN_PROGRESS`.
- Location y Equipment son opcionales; no convertirlos en requisitos para enviar el formulario.

## 3. Support Agent · Support Inbox y claim

La bandeja del agente es una sola pantalla con dos pestañas. **Available** representa tickets abiertos sin asignación; **Assigned to me** muestra el trabajo que ya pertenece al agente autenticado.

~~~mermaid
flowchart TD
    A[Support Inbox] --> B{Pestaña seleccionada}
    B -- Available --> C[Listar tickets OPEN sin asignar]
    C --> D[Mostrar solo resumen permitido]
    D --> E[Seleccionar ticket]
    E --> F[Claim]
    F --> G{Resultado del claim}
    G -- 200 Success --> H[Asignación confirmada]
    H --> I[Actualizar Available y Assigned to me]
    I --> J[Ticket Detail]
    G -- 409 Conflict --> K[Otro agente lo reclamó]
    K --> L[Actualizar la bandeja]
    L --> C
    G -- 403 / 404 --> M[Mostrar acceso no permitido o recurso no disponible]
    M --> L
    B -- Assigned to me --> N[Listar tickets asignados al agente actual]
    N --> O[Seleccionar ticket]
    O --> J
    J --> P{Estado del ticket}
    P -- ASSIGNED --> Q[Start work]
    Q --> R[IN_PROGRESS]
    P -- IN_PROGRESS --> S[Continuar atención]
    R --> S
    S --> T[Resolver ticket]
    T --> U[RESOLVED]
~~~

**Reglas de la bandeja**

- Las pestañas son **Available** y **Assigned to me** dentro de Support Inbox; no son dos productos ni dos sistemas de navegación.
- **Available** solo muestra tickets OPEN sin asignación y únicamente los campos de resumen permitidos. No debe filtrar mensajes ni descripciones privadas.
- Claim es una acción explícita. No usar drag-and-drop como mecanismo de asignación.
- El claim es atómico en backend. Un solo agente gana; los demás reciben 409 Conflict, actualizan la lista y no ven una falsa confirmación.
- **Assigned to me** se calcula desde la identidad autenticada. No aceptar un assigneeId arbitrario enviado por el navegador.
- No agregar búsqueda global, filtros por agente/categoría ni métricas si el contrato no los soporta.
- El agente asignado puede avanzar el trabajo y resolver según las transiciones permitidas.

## 4. Ticket Detail · Conversation y Activity

Ticket Detail separa la conversación humana del historial de eventos del sistema. En desktop la conversación es el área principal y los detalles/Activity ocupan un panel lateral. En mobile, Conversation y Details son tabs; Activity permanece como sección independiente dentro de Details.

~~~mermaid
flowchart TD
    A[Abrir Ticket Detail] --> B[Verificar sesión y permisos]
    B --> C{Acceso autorizado?}
    C -- No --> D[Mostrar recurso no disponible o acceso denegado]
    C -- Sí --> E[Cargar ticket y detalles]
    E --> F[Cargar Activity]
    E --> G{Estado del ticket}
    G -- OPEN --> H[Chat no disponible: esperar asignación]
    G -- ASSIGNED --> I[Habilitar Conversation]
    G -- IN_PROGRESS --> I
    G -- RESOLVED --> J[Conversation de solo lectura]
    G -- CLOSED --> J
    G -- CANCELLED --> J
    I --> K[Escribir y enviar mensaje]
    K --> L[Chat valida sesión y permiso vigente]
    L --> M{Envío autorizado y persistido?}
    M -- Sí --> N[Confirmar mensaje y actualizar Conversation]
    M -- No --> O[Mostrar error; no afirmar que se envió]
    N --> P[Actualizar mensajes en tiempo real]
    O --> I
    H --> F
    J --> F
    F --> Q[Mostrar timeline cronológico separado]
~~~

**Separación de áreas**

| Área | Contenido | Comportamiento |
| --- | --- | --- |
| **Conversation** | Mensajes enviados por Reporter y participantes autorizados | Escritura habilitada solo en estados permitidos; historial de solo lectura al resolver/cerrar/cancelar |
| **Activity** | Creación, claim, reasignación, cambios de estado y otros eventos auditables | Timeline cronológico; no admite escribir mensajes |
| **Details** | Categoría, estado, fecha, Reporter, agente asignado y datos opcionales permitidos | Datos sujetos a autorización y disponibilidad contractual |

**Reglas por estado**

| Estado | Conversation | Activity |
| --- | --- | --- |
| OPEN | No hay sala de chat disponible; mostrar indicación de que se habilita tras la asignación | Visible para actores autorizados |
| ASSIGNED | Escritura permitida a participantes autorizados | Visible y separada |
| IN_PROGRESS | Escritura permitida a participantes autorizados | Visible y separada |
| RESOLVED | Historial de solo lectura | Visible y separada |
| CLOSED | Historial de solo lectura | Visible y separada |
| CANCELLED | Historial de solo lectura | Visible y separada |

- La matriz de requisitos contempla al Reporter dueño, al agente asignado y al Admin activo para acceder al chat del ticket; cada operación debe revalidarse en backend.
- La reasignación retira al agente anterior de las nuevas operaciones y de futuras emisiones; un evento de NATS no concede permisos.
- Si Auth, Tickets o Chat no puede confirmar una autorización necesaria, la UI muestra un fallo temporal y no habilita la operación.
- Tras reconectar, recuperar el historial desde el servidor. No tratar una notificación Socket.IO como fuente única de verdad.
- Los archivos adjuntos pertenecen a la evidencia del ticket, no se insertan automáticamente como mensajes de chat.

## 5. Admin · Supervisión y gestión de cuentas

Admin tiene dos áreas separadas: **All Tickets** para supervisión de incidencias y **User Management** para cuentas. Las acciones sensibles deben confirmar su resultado desde el servidor y dejar auditoría.

### 5.1 Supervisar y reasignar tickets

~~~mermaid
flowchart TD
    A[All Tickets] --> B[Seleccionar ticket]
    B --> C[Ticket Detail]
    C --> D[Revisar estado, responsable y Activity]
    D --> E{Necesita reasignación?}
    E -- No --> F[Volver a All Tickets]
    E -- Sí --> G[Elegir Support Agent activo]
    G --> H[Introducir motivo]
    H --> I[Confirmar reasignación]
    I --> J{Backend valida versión y agente?}
    J -- Sí --> K[Actualizar assignee y registrar Activity]
    K --> L[Refrescar detalle y bandejas]
    J -- No: 409 --> M[Mostrar conflicto y recargar estado]
    J -- No: 422 / 503 --> N[Mostrar validación o fallo temporal]
    M --> C
    N --> C
~~~

- Reasignar es una acción Admin; exige motivo y control de versión según el contrato.
- El agente destino debe ser una cuenta Support Agent activa.
- La UI no presenta la reasignación como exitosa hasta recibir confirmación.
- Tras confirmar, actualizar responsable, Activity y vistas de bandeja. El agente anterior no debe recibir nuevas operaciones o broadcasts del ticket.

### 5.2 Crear, resetear, desactivar y reactivar cuentas

~~~mermaid
flowchart TD
    A[User Management] --> B{Acción}
    B -- Crear --> C[Create account]
    C --> D[Email, display name y rol permitido]
    D --> E[Crear Reporter o Support Agent]
    E --> F[Mostrar temporary password una sola vez]
    F --> G[Entregar por canal seguro]
    B -- Resetear --> H[Seleccionar cuenta habilitada]
    H --> I[Emitir nueva contraseña temporal]
    I --> F
    B -- Desactivar --> J[Confirmar disable]
    J --> K[Marcar DISABLED y revocar sesiones]
    K --> L[Conservar tickets, mensajes e historial]
    B -- Reactivar --> M[Seleccionar cuenta DISABLED]
    M --> N[Reactivar con nueva contraseña temporal]
    N --> F
    G --> O[Usuario inicia sesión]
    O --> P[Password change-only]
    P --> Q[Activar contraseña personal]
    Q --> R[Invalidar sesión provisional]
    R --> S[Volver a Sign in]
    S --> T[Login normal y sesión FULL]
~~~

**Reglas de gestión de cuentas**

- Los roles asignables desde Admin son REPORTER y SUPPORT_AGENT; no se crea otro Admin por esta pantalla.
- La contraseña temporal se muestra una sola vez. Nunca debe persistirse en logs, historial de navegación o pantallas recuperables.
- La primera autenticación con contraseña temporal conduce a Password change-only, sin acceso a Tickets ni Chat.
- Después del cambio, la sesión provisional se revoca y el usuario debe iniciar sesión de nuevo.
- Desactivar una cuenta revoca sus sesiones, pero no elimina sus tickets, mensajes ni historial.
- Una cuenta desactivada debe reactivarse antes de resetearla; la reactivación emite una nueva contraseña temporal.
- No hay autorregistro, edición de roles ni recuperación autónoma por email en el MVP.

## 6. Ciclo de vida del ticket

Este diagrama resume el ciclo de vida presentado en las vistas. Las operaciones de asignación, cambio de estado, cierre y cancelación deben respetar actor, ownership, estado actual y control de versión en backend.

~~~mermaid
stateDiagram-v2
    [*] --> OPEN: Reporter crea ticket
    OPEN --> ASSIGNED: Support Agent reclama
    OPEN --> CANCELLED: Reporter dueño o Admin cancela
    ASSIGNED --> IN_PROGRESS: Agente asignado inicia atención
    IN_PROGRESS --> RESOLVED: Agente asignado resuelve
    ASSIGNED --> RESOLVED: Admin resuelve excepcionalmente
    IN_PROGRESS --> RESOLVED: Admin resuelve excepcionalmente
    RESOLVED --> CLOSED: Reporter dueño confirma cierre
    RESOLVED --> CLOSED: Admin realiza cierre excepcional auditado
    ASSIGNED --> ASSIGNED: Admin reasigna responsable
    IN_PROGRESS --> IN_PROGRESS: Admin reasigna responsable
    CLOSED --> [*]
    CANCELLED --> [*]
~~~

No se diseña reapertura de tickets para el MVP. Una reasignación cambia el responsable y deja auditoría; no debe inventar un estado nuevo.

## 7. Estados transversales que deben diseñarse

Estos estados se aplican a las vistas y acciones anteriores, no son pantallas de negocio adicionales.

| Situación | Respuesta de UI |
| --- | --- |
| Carga inicial | Skeletons con la estructura real del contenido |
| Lista vacía | Empty state que explica qué hacer a continuación |
| Sin resultados por filtro | Empty state con acción para limpiar el filtro |
| Validación 422 | Mensaje junto al campo que debe corregirse |
| Sesión 401 | Volver a Sign in y limpiar datos protegidos en memoria |
| Sin permiso 403 | Explicar que la acción no está permitida; no revelar datos |
| Recurso no disponible 404 | Estado neutral que no filtre la existencia de tickets ajenos |
| Conflicto 409 | Refrescar el recurso y explicar que cambió o fue reclamado |
| Rate limit 429 | Mensaje de espera sin reintentos agresivos |
| Dependencia caída 503 | Error temporal con retry seguro; no mostrar éxito falso |
| Acción pendiente | Deshabilitar doble envío y mostrar progreso |
| Éxito | Confirmación breve y actualización de la vista afectada |
| Chat reconectando | Indicar reconexión y reconciliar historial desde servidor |

## 8. Decisiones UX aprobadas y validación pendiente

### Aprobadas por el usuario

- Dirección visual **B — Campus / Warm**.
- Desktop y mobile con la misma prioridad.
- UI en inglés.
- Support Inbox con pestañas **Available / Assigned to me**.
- Activity independiente de Conversation/Chat.
- Location y Equipment dentro de **Additional details (optional)** colapsable.
- El brief de UI/UX queda aprobado como base para los mockups high-fidelity.

### Baseline congelada; comportamiento aún no implementado

- Campo de urgencia, campo/operación de prioridad oficial y foto/video multiarchivo están reflejados en la baseline Contract-First 0.2.0 congelada por el usuario.
- Validación real de MIME, cuotas, permisos, streaming privado y concurrencia de prioridad/adjuntos sigue pendiente de implementar y probar.
- Cualquier endpoint o comportamiento que no aparezca en el contrato vigente.
- El frontend y sus componentes: este repositorio continúa sin aplicación integrada en esta rama documental.

El usuario congeló la baseline 0.2.0 y su commit de la baseline en `dev` quedó registrado antes de los controladores. La revisión técnica de Valeria/Rina puede registrarse después y no se les atribuye aceptación anticipada. La UI puede avanzar con fixtures tipados; cualquier cambio de contrato requiere nueva versión. Cualquier cambio al contrato requiere una nueva versión conforme a [G1 B3](010.G1-Contracts.md).
