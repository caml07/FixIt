**Horizonte:** desde el 10 de noviembre de 2026 hasta la semana del **7 al 11 de diciembre de 2026** para Web Development II (presentaciones indicadas en el silabo oficial; una actividad el dia 7). **Fechas y horas de entrega todavia por confirmar** con los docentes. ## Regla de ejecución

**Una sola aplicación, dos demostraciones principales y un track academico adicional:**
- **Web II:** tickets + RBAC + concurrencia + WebSockets + persistencia + pruebas + OpenAPI.
- **Cloud:** arquitectura AWS, VPC, IAM, EC2, S3 Versioning, EBS, monitoreo, seguridad, costos y recuperabilidad.
- **Software Engineering II (principalmente Valeria y Rina):** posible reutilizacion del modelo DDD; no bloquear los entregables de Web II/Cloud por requisitos sin confirmar de otra materia.

No duplicar código ni crear dos proyectos paralelos. No desplegar versiones de un backend que todavía no funciona localmente.

**Estado y bloqueos actualizados:** consultar [011.Gates](011.Gates.md). Diseño seleccionado por usuario: **Auth + Tickets + Chat + NATS JetStream**, no el candidato historico de dos servicios. El usuario reporto que **Marvin acepta una VPC + una EC2 y espera evidencia de S3**; la modalidad exacta sigue pendiente. No existe codigo de producto. En el host se detecto Podman, pero falta proveedor Compose. **Gates = checkpoints de evidencia, no fases rigidas de microaprobaciones**. Las fechas de fases siguientes son hipotesis de plan, no compromisos; el usuario decidio **no implementar todavia**.

**Instruccion nueva de COP3851, 11 nov:** la [hoja Contract-First de Felix](references/COP3851_Capstone_2026-11-11.md) exige **OpenAPI y esquema 3NF con FK/migraciones commiteados antes de que agentes de IA generen endpoints de backend**. Las reglas de agentes estan centralizadas en [CONTEXT.md](../CONTEXT.md); la exigencia literal de nombre `CLAUDE.md`/`GEMINI.md` se verificara con Felix, sin duplicar la constitucion. El spike previo **no** es una API de producto ni demuestra el cumplimiento; sus resultados estan consolidados en [013](013.Spike-Results.md). Preparar primero contratos + esquema, revisarlos y pedir commit al usuario; luego generar controladores. Dependencias nuevas de backend requieren **[DEPENDENCY RFC] + npm audit**. Reservar evidencia de ataques red-team y practica de defensa en vivo (50% de la evaluacion conjunta: contrato/schema + seguridad).

## Flujo Git y evidencia de colaboración

- `main`: estable/protegida. `dev`: integración tras PR. `feat/*`: trabajo aislado; PR hacia `dev` con reviewer y verificación.
- Commits pequeños y significativos vinculados a FR/NFR o ticket. No auto-commit ni push por acción del agente sin permiso explícito.
- PR con objetivo, screenshot/log de evidencia cuando aplique, pruebas ejecutadas y riesgos. Mantener un changelog sencillo por release; no duplicar toda discusión en cinco archivos.
- Cada despliegue a S3 y EC2 relaciona `git SHA`, archivo checksum y fecha, sin llaves ni dumps de datos reales en S3 `releases/`.

## Riesgos y mitigación

| Riesgo | Impacto | Acción anterior a la demo |
| --- | --- | --- |
| Incompatibilidad cuenta AWS Free / costo real | Alto | Revisión inicial con Marvin + Calculator antes de crear recursos |
| Dual PostgreSQL + MongoDB consume mucha RAM | Alto | Perfil local, ajustar tamaño/conversar simplificación ADR-002 |
| Falta de dominio/HTTPS para API con cookies | Alto | Resolver temprano DNS/certificado; no habilitar HTTP público |
| Varias funcionalidades grandes al mismo tiempo | Alto | Gate F1 antes de abrir chat y Cloud |
| Instancia detenida durante demo | Alto | Owner de operación, aviso + ventana de demo |
| Acceso transversal a mensajes/IDOR | Alto | Pruebas negativas de HTTP y Socket.io |
| Corrupción de DB o despliegue fallido | Alto | backup + restore + release por SHA |
| Subir demasiado a S3 con versiones | Medio | Lifecycle, control de artefactos y alertas |
| Desacuerdos sobre requisitos de cursos | Alto | Confirmar rúbricas exactas con Félix y Marvin |

## DoD — definición de terminado

Una funcionalidad solo está «Done» si: requisito identificado, permisos y errores implementados, prueba correspondiente ejecutada, README/OpenAPI al día y demo manual verificable. Cloud solo está «Done» si tiene evidencias reales de infraestructura desplegada, costos observados y cleanup plan; no por tener un diagrama.
