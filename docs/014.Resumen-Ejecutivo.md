# FixIt — Resumen ejecutivo y guía de presentación

**Versión:** 11 de noviembre de 2026. **Presentaciones previstas:** Marvin y Mr. Félix el 12 de noviembre; Valeria y Rina cuando el equipo pueda reunirse.

**Estado honesto:** el usuario ha seleccionado el alcance y la arquitectura para revisarlos con el equipo. **No existe aplicación implementada, OpenAPI formal, migraciones del producto ni infraestructura AWS desplegada. Ningún gate G0–G5 tiene PASS.** Las pruebas históricas de spikes no equivalen a una aplicación funcionando.

## 1. El proyecto en un minuto

**FixIt** es una aplicación web de soporte técnico (**IT Help Desk**) para una institución. Convierte problemas de Wi-Fi, computadoras, software, cuentas, proyectores y periféricos en **tickets trazables** en lugar de dejarlos perdidos en conversaciones o WhatsApp. El usuario reporta, un agente de soporte reclama el ticket, ambos conversan dentro del caso y registran cómo se resuelve. Admin administra cuentas, supervisa la cola y puede reasignar.

**Resultado buscado:** cada incidente tiene propietario, responsable, estado, historial y conversación; no se duplica la asignación cuando dos agentes compiten por un ticket.

Se construirá un **MVP pequeño pero completo**, no todo el sistema de mantenimiento de instalaciones con IA descrito en el PDF original. La aplicación sirve al proyecto Web Development II y a la demostración Cloud, mientras Valeria y Rina validan por separado su alineación con Software Engineering II.

## 2. Alcance funcional del MVP

| Actor | Funcionalidad principal |
| --- | --- |
| **Reporter** | Login, crear ticket IT, foto **opcional**, editar título/descripción/categoría cuando esté `OPEN`, seguir el estado, chatear y confirmar cierre |
| **Support Agent** | Ver cola de casos libres, **reclamar atómicamente** un ticket, atender asignados, conversar, actualizar estado |
| **Admin** | Crear cuentas, gestionar categorías limitadas, ver cola, recibir avisos de tickets nuevos, asignar/reasignar con auditoría, intervenir cuando corresponde |

**Estados:** `OPEN -> ASSIGNED -> IN_PROGRESS -> RESOLVED -> CLOSED`; `CANCELLED` desde `OPEN`. Transiciones y cambios importantes guardan actor, fecha e historial. Dos agentes que reclaman el mismo ticket dan un ganador y un conflicto, no dos asignaciones.

**Fotografías:** evidencia **opcional** vinculada al ticket, nunca al token/sesión. Límite conservador **propuesto**: una foto JPG/PNG/WebP, máximo **5 MB**, acceso privado, comprobación del contenido y autorización de lectura/descarga. El almacenamiento específico (volumen protegido o S3 privado) no se ha elegido; no asumir que usar fotos obliga a cambiar el uso académico de S3.

**Notificaciones dentro de la aplicación:** nuevos tickets para Admin; asignación/reasignación, cambios de estado y mensajes nuevos para participantes autorizados. Se recupera el estado y el historial al reconectar. **No hay** correo/push, bandeja histórica independiente ni garantía de que Socket.IO reproduzca todos los broadcasts.

**Fuera del MVP:** triage IA, mantenimiento eléctrico/HVAC/plomería, análisis de peligros, inventario, SLA, CSV, dashboard avanzado, calificaciones, múltiples organizaciones, autoregistro, app móvil nativa y chat libre fuera de tickets. Ubicación o equipo son atributos opcionales del incidente, no parte de la identidad.

## 3. Arquitectura acordada para revisión del equipo

~~~mermaid
flowchart TB
  User[Reporter / Agent / Admin] -->|HTTPS + WSS| Proxy[Proxy HTTPS y React/Vite]
  Proxy --> Auth[Auth / Express]
  Proxy --> Tickets[Tickets / Express]
  Proxy --> Chat[Chat / Express + Socket.IO]
  Tickets -.->|REST privado: identidad| Auth
  Chat -.->|REST privado: identidad| Auth
  Chat -.->|REST privado: permisos| Tickets
  Auth --> PG[(PostgreSQL: schemas auth y tickets)]
  Tickets --> PG
  Chat --> Mongo[(MongoDB: mensajes)]
  Tickets -->|Outbox y publicador| NATS[(NATS JetStream)]
  NATS -->|Eventos de ticket| Chat
~~~

**Auth** gestiona identidades, roles y sesiones. **Tickets** decide propietario, asignación, estado y permisos por ticket. **Chat** persiste mensajes en MongoDB y usa Socket.IO, pero consulta **permisos vigentes** a Tickets/Auth; un evento de NATS nunca concede acceso. Los tres servicios son **runtimes independientes**. Auth/Tickets comparten **una base PostgreSQL** con esquemas `auth` y `tickets`, FK entre esquemas y privilegios de servicio separados.

**Persistencia propuesta (12 nov, pendiente de equipo):** **Prisma ORM**
para PostgreSQL con `auth.users`, `auth.sessions`,
`auth.account_audit`, `tickets.categories`,
`tickets.support_tickets`, `tickets.ticket_timeline`,
`tickets.outbox` y `tickets.ticket_attachments` (solo metadatos
de foto). **Una sola cadena de migraciones coordinada**, aunque los
servicios usen clientes y credenciales de mínimo privilegio distintos.
**Mongoose** para MongoDB de Chat: documentos `messages` con
`ticketId`, `senderId`, `clientMessageId`, texto y fecha; inbox
idempotente de eventos cuando corresponda. El `ticketId` no es FK entre
MongoDB y PostgreSQL: los permisos se consultan por REST a Tickets.
**No existen aún los esquemas ejecutables**.

**Decisión de canales:** REST privado y sincrónico para identidad y autorización; **NATS JetStream** para eventos de Tickets; Socket.IO para entrega en vivo al navegador. PostgreSQL guarda **ticket + timeline + outbox en una sola transacción** y responde al usuario sin esperar ACK de NATS. Después se publica con reintentos; Chat deduplica por `eventId`, compara `aggregateVersion` y reconcilia. Hay **consistencia eventual de notificaciones**, pero **no de permisos**. No se promete `exactly-once`.

**Reasignación:** las operaciones nuevas del antiguo agente se niegan; operaciones ya autorizadas y en vuelo pueden completarse bajo la política B2 elegida, pendiente de pruebas y ratificación del equipo. **Alternativa de contingencia**, solo si G2 o los plazos lo exigen: unir Auth y Tickets, conservar Chat; no es el diseño seleccionado.

## 4. Identidad, seguridad y credenciales

No hay registro público. **Admin crea cuentas**. El primer Admin se aprovisionará mediante un **seeder inicial idempotente**, sin contraseña fija en Git. Las contraseñas temporales serán aleatorias y válidas por **72 horas**; el usuario entra en estado `PASSWORD_CHANGE_ONLY` sin acceso a Tickets/Chat, cambia la contraseña, invalida el acceso provisional y vuelve a iniciar sesión.

**Sesiones opacas**, cookies `HttpOnly; Secure; SameSite=Strict`, comprobación de CSRF/Origin, rate limiting, RBAC, ownership por ticket y autorización en endpoints y sockets. Política objetivo **NIST SP 800-63B-4**: mínimo 15 caracteres sin MFA, admitir 64 o más, Unicode y espacios, blocklist y sin reglas artificiales de composición ni rotación periódica. **Pendiente técnico antes de Auth:** bcrypt sigue siendo candidato académico, pero su límite habitual de **72 bytes** requiere resolver la verificación íntegra de contraseñas largas y Unicode; Argon2id es alternativa. No afirmar que se ha implementado ni certificado la política.

**Seguridad de fotos:** validar tamaño, formato real, privacidad y acceso por ticket. No publicar fotos/DB/broker directamente en Internet. Para la demo se usarán datos ficticios.

## 5. Propuesta Cloud para Marvin

**Confirmación oral reportada por el usuario (11-12 nov): Marvin acepta una VPC y una EC2 y el 12 nov dio luz verde para continuar con la arquitectura de Cloud**, además de esperar evidencia de **S3**. Esto prevalece en nuestra planificación sobre el PDF complementario de 23 páginas que propone dos VPC, peering y dos VM; **no significa aprobación de costos reales, provisión de recursos ni PASS de G5**. Las decisiones operativas intermedias para revisión del equipo constan en la [sección 8 de Cloud](004.Cloud.md).

**Topología candidata:** una EC2 Linux con contenedores para proxy HTTPS, React compilado, Auth, Tickets, Chat, NATS, PostgreSQL y MongoDB. Solo publicar 443 (y 80 si se requiere para redirección/certificados); API privada, bases de datos y broker detrás del proxy. Identidad AWS individual con MFA, IAM mínimo, SSM si es viable, logs, monitoreo, health checks, backup/restore y cleanup. Una EC2 es un **punto único de fallo** aceptado para demo, **no alta disponibilidad**.

**Tamaño y presupuesto:** `t3.medium` (2 vCPU/4 GiB) es solo una candidata; **falta medir** RAM/CPU reales y verificar elegibilidad de cuenta, región, EC2/EBS, IPv4 pública, S3, monitoreo y costos. Ningún plan de pago o despliegue está autorizado por la documentación.

**S3 tiene dos interpretaciones distintas:** el diseño actual propone un **bucket privado con Versioning** para artefactos de despliegue identificados por commit SHA y demostración de rollback. El PDF complementario propone una **página estática pública alojada en S3**. Todavía hay que preguntar a Marvin si exige **versiones privadas, website estático o ambos**. El website endpoint nativo de S3 no ofrece HTTPS; no alojar login ni información sensible mediante HTTP plano.

**Para la reunión del 12 nov:** confirmar modalidad S3; qué capturas/pruebas sustituyen segunda VPC/VM y peering; si requieren IAM/MFA, CloudWatch/SNS, ping, calculadora anual de costo, video y reportes; **fechas/horas exactas**; presupuesto y ventana de eliminación de recursos.

## 8. Estado de gates y secuencia de ejecución

| Gate | Estado | Qué habilita el avance |
| --- | --- | --- |
| **G0 — academia/scope** | Parcial | Consultas a Marvin/Félix; SE II lo validan Valeria/Rina |
| **G1 — arquitectura/contratos** | Diseño seleccionado por usuario, equipo pendiente | Revisión con Valeria/Rina; resolver hashing/bootstrap y luego contrato formal antes del código |
| **G2 — capacidad/costos** | Spikes históricos, no producto probado | Perfil de RAM/CPU/costos, backups y carga sobre MVP real antes de AWS |
| **G3 — seguridad/consistencia** | Diseño de riesgos y pruebas, sin PASS | Tests de revocación, asignación concurrente, fallos, BOLA/IDOR, injection, CORS y rate limit sobre producto |
| **G4 — implementación** | No iniciada | Autorización de implementación, commit Contract-First, backend/frontend, test suite, CI/demo |
| **G5 — Cloud/entrega** | Una VPC/EC2 aceptadas oralmente; no desplegado | Presupuesto aprobado, EC2/S3/monitorización/evidencias, restauración y cleanup |

**Secuencia al autorizar implementación:** acordar requisitos docentes y revisión G1 de equipo; elaborar y commitear contratos OpenAPI/3NF/FK; construir `login -> ticket/foto -> claim -> chat -> estado/avisos -> cierre`; probar permisos, eventos y resiliencia; medir costos; desplegar AWS con autorización; documentar red team, capturas y defensa.

**Criterio de éxito:** una persona reporta un incidente de TI y sigue su estado, un agente lo toma sin duplicarse, ambos conversan con autorización correcta, Admin supervisa y el equipo muestra por qué el sistema es seguro, reproducible y operable.
