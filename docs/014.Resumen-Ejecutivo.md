## 1. El proyecto en un minuto

**FixIt** es una aplicacion web de soporte tecnico (**IT Help Desk**) **single-tenant para Keiser University LAC**, como piloto academico (no despliegue oficial aprobado). Convierte problemas de Wi-Fi, computadoras, software, cuentas, proyectores y periféricos en **tickets trazables** en lugar de dejarlos perdidos en conversaciones o WhatsApp. El usuario reporta, un agente de soporte reclama el ticket, ambos conversan dentro del caso y registran cómo se resuelve. Admin administra cuentas, supervisa la cola y puede reasignar.

**Resultado buscado:** cada incidente tiene propietario, responsable, estado, historial y conversación; no se duplica la asignación cuando dos agentes compiten por un ticket.

Se construirá un **MVP pequeño pero completo**, no todo el sistema de mantenimiento de instalaciones con IA descrito en el PDF original. La aplicación sirve al proyecto Web Development II y a la demostración Cloud, mientras Valeria y Rina validan por separado su alineación con Software Engineering II.

## 2. Alcance funcional del MVP

| Actor | Funcionalidad principal |
| --- | --- |
| **Reporter** | Login, crear ticket con hora, tag, descripción, fotos/video y **propuesta de urgencia** (no prioridad final); editar OPEN, consultar, chatear, confirmar cierre |
| **Support Agent** | Ver cola de casos libres, **reclamar atómicamente** un ticket, atender asignados, conversar, actualizar estado |
| **Admin** | Listar/crear cuentas personales, restablecer contrasenas y desactivar/reactivar accesos con auditoria; ver cola y reasignar tickets. Sin autorregistro ni cambios de rol en MVP |

**Estados:** `OPEN -> ASSIGNED -> IN_PROGRESS -> RESOLVED -> CLOSED`; `CANCELLED` desde `OPEN`. Transiciones y cambios importantes guardan actor, fecha e historial. Dos agentes que reclaman el mismo ticket dan un ganador y un conflicto, no dos asignaciones.

**Formulario revisado con Rina (17-18 nov, según usuario; defaults aprobados por usuario el 26 nov):** hora del servidor, Subject, **tag que utiliza categoría TI existente** (computadora/red/software/cuentas/periféricos), descripción breve de fallos, urgencia propuesta por Reporter y prioridad oficial manual por Support Agent asignado/Admin. Urgencia `LOW/NORMAL/HIGH`; prioridad `P1_CRITICAL/P2_HIGH/P3_NORMAL/P4_LOW`, inicialmente `NULL` y requerida antes de `IN_PROGRESS`. Evidencia opcional: hasta 5 archivos/2 videos; JPEG/PNG/WebP 5 MiB por imagen, MP4 25 MiB por video y 50 MiB total por ticket. Storage filesystem privado local y S3 privado cuando Cloud esté autorizado. El ejemplo «luz» no amplía el alcance ni exige un tag nuevo. La baseline OpenAPI/Prisma/SQL 0.2.0 está congelada por el usuario; Redocly, Prisma validate, smoke SQL PostgreSQL 17 y migrate diff vacío pasan. Falta revisión técnica de Valeria/Rina, pruebas de aplicación. IA futura.

**Notificaciones dentro de la aplicación:** nuevos tickets para Admin; asignación/reasignación, cambios de estado y mensajes nuevos para participantes autorizados. Se recupera el estado y el historial al reconectar. **No hay** correo/push, bandeja histórica independiente ni garantía de que Socket.IO reproduzca todos los broadcasts.

**Fuera del MVP:** triage IA, mantenimiento de instalaciones (el ejemplo «luz» no es nueva categoría), análisis de peligros, inventario, SLA, CSV, dashboard avanzado, calificaciones, múltiples organizaciones, autorregistro, app móvil nativa y chat libre fuera de tickets. Ubicación/equipo son atributos opcionales, no parte de la identidad.

## 3. Arquitectura acordada para revisión del equipo

~~~mermaid
flowchart TB
  User[Reporter / Agent / Admin] -->|HTTPS + WSS| Proxy[Proxy HTTPS y React/Vite]
  Proxy --> Auth[Auth / Express]
  Proxy --> Tickets[Tickets / Express]
  Proxy --> Chat[Chat / Express + Socket.IO]
  Tickets -.->|REST privado: identidad| Auth
  Chat -.->|REST privado: identidad| Auth
  Chat -.->|REST privado: permisos| Tickets
  Auth --> PG[(PostgreSQL: schemas auth y tickets)]
  Tickets --> PG
  Chat --> Mongo[(MongoDB: mensajes)]
  Tickets -->|Outbox y publicador| NATS[(NATS JetStream)]
  NATS -->|Eventos de ticket| Chat
~~~

**Auth** gestiona identidades, roles y sesiones. **Tickets** decide propietario, asignación, estado y permisos por ticket. **Chat** persiste mensajes en MongoDB y usa Socket.IO, pero consulta **permisos vigentes** a Tickets/Auth; un evento de NATS nunca concede acceso. Los tres servicios son **runtimes independientes**. Auth/Tickets comparten **una base PostgreSQL** con esquemas `auth` y `tickets`, FK entre esquemas y privilegios de servicio separados.

**Persistencia propuesta (12 nov, pendiente de equipo):** **Prisma ORM**
para PostgreSQL con `auth.users`, `auth.sessions`,
`auth.account_audit`, `tickets.categories`,
`tickets.support_tickets`, `tickets.ticket_timeline`,
`tickets.outbox` y `tickets.ticket_attachments` (solo metadatos
de foto). **Una sola cadena de migraciones coordinada**, aunque los
servicios usen clientes y credenciales de mínimo privilegio distintos.
**Mongoose** para MongoDB de Chat: documentos `messages` con
`ticketId`, `senderId`, `clientMessageId`, texto y fecha; inbox
idempotente de eventos cuando corresponda. El `ticketId` no es FK entre
MongoDB y PostgreSQL: los permisos se consultan por REST a Tickets.
**No existen aún los esquemas ejecutables**.

**Decisión de canales:** REST privado y sincrónico para identidad y autorización; **NATS JetStream** para eventos de Tickets; Socket.IO para entrega en vivo al navegador. PostgreSQL guarda **ticket + timeline + outbox en una sola transacción** y responde al usuario sin esperar ACK de NATS. Después se publica con reintentos; Chat deduplica por `eventId`, compara `aggregateVersion` y reconcilia. Hay **consistencia eventual de notificaciones**, pero **no de permisos**. No se promete `exactly-once`.

**Reasignación:** las operaciones nuevas del antiguo agente se niegan; operaciones ya autorizadas y en vuelo pueden completarse bajo la política B2 elegida, pendiente de pruebas y ratificación del equipo. **Alternativa de contingencia**, solo si G2 o los plazos lo exigen: unir Auth y Tickets, conservar Chat; no es el diseño seleccionado.

## 4. Identidad, seguridad y credenciales

No hay registro público. **Admin crea cuentas**. El primer Admin se aprovisionará mediante un **seeder inicial idempotente**, sin contraseña fija en Git. Si se pierde o vence la temporal del primer Admin, un **comando administrativo local y manual** recupera esa misma cuenta, revoca sesiones y audita; no se crea segundo Admin. Las contraseñas temporales serán aleatorias y válidas por **72 horas**; el usuario entra en estado `PASSWORD_CHANGE_ONLY` sin acceso a Tickets/Chat, cambia la contraseña, invalida el acceso provisional y vuelve a iniciar sesión.

**Sesiones opacas**, cookies `HttpOnly; Secure; SameSite=Strict`, CSRF/Origin, rate limiting, RBAC y ownership por ticket. Politica objetivo **NIST SP 800-63B-4**: minimo 15 caracteres sin MFA, admitir 64 o mas, Unicode y espacios, blocklist y sin composicion ni rotacion periodica arbitrarias. **Argon2id elegido el 15 nov** para hashes del producto; calibracion de RAM/CPU y pruebas pendientes. Bcrypt queda como practica/benchmark academico historico. No afirmar implementacion ni certificacion.

**Seguridad de fotos:** validar tamaño, formato real, privacidad y acceso por ticket. No publicar fotos/DB/broker directamente en Internet. Para la demo se usarán datos ficticios.

## 5. Propuesta Cloud para Marvin

**Confirmación oral reportada por el usuario (11-12 nov): Marvin acepta una VPC y una EC2 y el 12 nov dio luz verde para continuar con la arquitectura de Cloud**, además de esperar evidencia de **S3**. Esto prevalece en nuestra planificación sobre el PDF complementario de 23 páginas que propone dos VPC, peering y dos VM; **no significa aprobación de costos reales, provisión de recursos ni PASS de G5**. Las decisiones operativas intermedias para revisión del equipo constan en la [sección 8 de Cloud](004.Cloud.md).

**Topologia candidata:** una EC2 Linux con proxy, React compilado, Auth, Tickets, Chat, NATS, PostgreSQL y MongoDB en contenedores. **Acceso publico seleccionado por el usuario:** dominio DigitalPlat delegado a Cloudflare DNS y Tunnel nombrado por salida `cloudflared` hacia el proxy, **sin abrir 443/80 inbound por defecto**. API interna, bases y broker privados. Identidad AWS individual con MFA, IAM mínimo, SSM si es viable, logs, monitoreo, health checks, backup/restore y cleanup. Una EC2 es un **punto único de fallo** aceptado para demo, **no alta disponibilidad**.

**Computo para pruebas:** el usuario eligio **EC2 Spot `persistent`/EBS-backed** con stop/start manual y `stop` en interrupciones. **On-Demand solo para presentaciones cuando Spot no este disponible**, lanzando una nueva EC2 desde configuracion reproducible y restaurando datos; no conversion in-place. Spot no se detiene por inactividad y EBS/S3 siguen cobrando detenida. `t3.medium` (2 vCPU/4 GiB) es candidata; falta medir RAM/CPU, elegibilidad/stop-start Spot, salida EC2, S3 y monitoreo. Valeria pidio vigilar el costo. **Tope acordado: US$120 de costo AWS acumulado del proyecto, cubierto exclusivamente con creditos AWS realmente disponibles**, sin gasto personal autorizado. US$200 es la promocion maxima posible, no saldo garantizado. No provisionar ni cambiar a Paid sin preflight y permiso.

**Publicacion Cloudflare no esta provisionada:** el usuario administrara DigitalPlat/Cloudflare y Valeria tendra acceso delegado si el plan lo admite, con MFA individual. Dominio, delegacion DNS, credenciales y salida de EC2 sin verificar. Tampoco se ha demostrado que esta via elimine costos de IPv4/NAT. Ver [Cloud, seccion 9](004.Cloud.md).

**S3 confirmado por el usuario (15 nov):** Marvin solicito **versionar la aplicacion**. Mantendremos bucket privado con **Versioning** de releases/manifiestos identificados por commit SHA para historial y rollback. El website S3 del PDF anterior no forma parte del alcance vigente. Versioning de releases NO es backup de PostgreSQL/MongoDB. **Backups de PG/Mongo privados, cifrados y conservados en un prefijo separado de S3** sin borrado automatico; al cierre se exporta copia segura antes de limpieza AWS, con aprobacion para cualquier borrado de backups.

**Para siguiente revision docente:** S3 Versioning ya aclarado; precisar evidencias de versiones/rollback y sustituciones de segunda VPC/VM del PDF antiguo, compatibilidad de Spot para demo, IAM/MFA, monitoreo, fechas y backups.
