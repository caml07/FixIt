## Acuerdos confirmados vs. hipótesis

**Confirmado en el diálogo:** scope IT Help Desk, chat *dentro del ticket*, agentes pueden tomar tickets disponibles, trabajo de los tres sobre bases de datos compartidas; Cloud corresponde académicamente a caml07 y Valeria, **Rina no cursó Cloud** según información más reciente; profesor Marvin sugirió S3 para gestionar versiones de artefactos en la nube. Ningún recurso AWS se ha creado.

**Propuesto por arquitectura (a validar entre los tres):** el monolito modular es la alternativa inicial documentada, pero el usuario quiere evaluar **EDA con microservicios** antes de aceptarla. El candidato EDA usa Core API + Chat Service + NATS JetStream sobre una EC2 **t3.medium** (2 vCPU, 4 GiB) con pruebas de memoria pendientes. Continúan propuestos React/Vite, PostgreSQL para tickets, MongoDB para mensajes, S3 privado/versionado, SSM e identidad AWS individual.

**Actualización G1 (10 nov, más reciente):** el usuario pasó a explorar **Auth Service + Ticket Service + Chat Service + NATS**, y seleccionó **sesiones opacas + bcrypt** como línea de diseño. No ha ratificado el equipo la arquitectura de tres servicios ni los contratos. Los documentos anteriores que dicen «dos servicios» representan **una alternativa histórica**; [009.HANDOFF](009.HANDOFF.md) prevalece como estado de la conversación hasta formalizar ADR/arquitectura.

**Profundización G1 (borrador, 10 nov):** [010.G1-Contracts](010.G1-Contracts.md) define límites de contextos, API interna, roles, eventos y riesgos abiertos; [ADR-005](adr/ADR-005-three-services-opaque-sessions.md) registra el trade-off de tres servicios sin marcarlo accepted. Ambas referencias son propuestas de revisión, no sustituyen el handoff ni los requisitos aprobados por el equipo.

**Seguimiento actual:** [CONTEXT.md](../CONTEXT.md) es la nota de continuidad; [011.Gates](011.Gates.md) registra qué falta para aprobar G0–G5; [012.G3](012.G3-Security-Consistency.md) documenta la primera regresión de seguridad comprobada en el spike. G2 final se postergó para avanzar G3/G4 localmente sin aprobar la infraestructura AWS. Al cerrarlos todos, recordar **actualizar** `CONTEXT.md`, revisar/crear `AGENTS.md` y sincronizar la documentación con lo efectivamente construido.

## Reglas de mantenimiento

- Cambios de alcance: editar 001 y marcar el ADR relacionado.
- Comportamiento: editar **solo** 002; arquitectura y contratos: 003; AWS/precios: 004; ejecución: 005.
- Cada FR/NFR tiene ID estable y prueba prevista; no renumerar IDs existentes.
- Cada ADR describe **estado** (proposed/accepted/superseded) y alternativa descartada; no convertir un borrador en acuerdo sin confirmación.
- No crear implementación, IAM, VPC, buckets ni cuentas por el hecho de estar descritos aquí.
- GitHub es la fuente de verdad del código y documentación. S3 guarda artefactos de despliegue identificados por commit, no sustituye Git.
- Documentos sin código ni infraestructura se etiquetan **diseño / no verificado**.
