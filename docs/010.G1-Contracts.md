# 010 · G1 — Contextos, contratos y autorizacion

**Estado: propuesta de trabajo, NO ADR aceptado, NO implementado.** Este documento especifica el candidato de **tres servicios** seleccionado por el usuario para explorar en G1. Requiere revision del equipo y no desplaza [003.Architecture](003.Architecture.md), [007.EDA-Evaluation](007.EDA-Evaluation.md) ni [ADR-004](adr/ADR-004-eda-two-services.md) hasta que se acepte un nuevo ADR. El MVP sigue siendo **IT Help Desk**, no mantenimiento de instalaciones.

## 1. Limites y lenguaje ubicuo

| Bounded context candidato | Servicio desplegable | Tipo DDD | Modelo y autoridad | No conoce |
| --- | --- | --- | --- | --- |
| Identity & Access | Auth | Generico | Account, Session, Role; credenciales, bcrypt, revocacion, login | Tickets, mensajes |
| IT Support Ticketing | Tickets | Core | SupportTicket, Assignment, TicketStatus, TicketTimeline, categoria, claim y policy de acceso por ticket | Password hashes, cuerpos de mensajes |
| Ticket Conversation | Chat | Supporting | Message, clientMessageId, historial, conexion Socket.io, entrega realtime | Estado autoritativo del ticket, roles globales |

**Un servicio no es automaticamente un bounded context.** Esta correspondencia es una propuesta deliberada de limites de modelo, no una inferencia por contenedores. Auth expone una identidad estable (userId y role); Tickets la traduce a Reporter / AssignedAgent / Admin para decisiones propias. Chat usa ticketId y senderId como referencias, sin compartir entidades ORM ni tablas.

**Terminologia del producto:** Reporter crea **SupportTicket**; Support Agent reclama uno sin asignar; Admin puede reasignar. No se usan WorkOrder, DISPATCHED, HazardPolicy, SLA ni AI triage del PDF adicional.

**Mapa de contextos (upstream -> downstream):**

~~~mermaid
flowchart LR
  Identity[Identity & Access<br/>generic] -->|Open Host Service: session introspection| Ticketing[IT Support Ticketing<br/>core]
  Identity -->|Open Host Service: session introspection| Conversation[Ticket Conversation<br/>supporting]
  Ticketing -->|Customer-Supplier: access policy API| Conversation
  Ticketing -->|Published Language: ticket events v1| Conversation
~~~

Los consumidores usan IDs y contratos publicos versionados, no el modelo ORM de otro contexto. El contrato de audiencia y acceso de Tickets es sincrono porque la autorizacion **no puede depender del retraso de la proyeccion de eventos**.

**Modelo DDD dentro de Tickets (MVP):**
- SupportTicket es aggregate root y protege OPEN -> ASSIGNED -> IN_PROGRESS -> RESOLVED -> CLOSED; OPEN -> CANCELLED. Reasignar no cambia status.
- Assignment y prioridad son conceptos del dominio; TicketTimeline es append-only. Un cambio de estado escribe el ticket, auditoria y outbox **en una transaccion PostgreSQL**.
- El claim usa UPDATE condicionado por status=OPEN y assigneeId IS NULL; no requiere leer y despues actualizar sin proteccion. Dos agentes compiten: exactamente un 200 y otro 409 en el test previsto.
- Ticket guarda userId externos emitidos por Auth; **no hay FK entre las bases de Auth y Tickets**.

### Cuestion academica: ¿dos contextos de negocio?

El PDF compartido por Valeria (pp. 9-21) propone **Intake** y **Maintenance** para facility maintenance; esa separacion depende de triage y WorkOrder, que NO pertenecen al MVP acordado.

Para Software Engineering II proponemos primero mostrar **Ticketing (core)** y **Conversation (supporting)** como dos modelos implementados, mas Identity (generic). Si el profesor pide expresamente **dos contextos de negocio/core ricos**, evaluar la alternativa **Issue Intake + Support Resolution** *como modulos dentro de ticket-service*: Intake poseeria IssueSubmission, Resolution poseeria SupportTicket, con traduccion explicita y un unico flujo de creacion; no crear un cuarto microservicio. Esta alternativa necesita justificar que IssueSubmission y SupportTicket son dos agregados genuinos y como se vinculan sin duplicar tickets visibles. **No esta aprobada** y no debe dibujarse como implementada. G0 bloquea esta decision academica.

## 2. Diagrama de dependencias (candidato)

~~~mermaid
flowchart TB
  Web[React/Vite] -->|HTTPS /api/v1| Proxy[Reverse proxy]
  Web -->|WSS /socket.io| Proxy
  Proxy --> Auth[Auth Express]
  Proxy --> Tickets[Tickets Express]
  Proxy --> Chat[Chat Express + Socket.io]
  Auth --> AuthPG[(PostgreSQL / Auth own schema or DB)]
  Tickets --> TicketPG[(PostgreSQL / Tickets own schema or DB)]
  Chat --> Mongo[(MongoDB / Chat)]
  Tickets -->|transactional outbox -> publish ACK| JS[NATS JetStream]
  JS -->|at-least-once| Chat
  Tickets -.->|internal introspection| Auth
  Chat -.->|handshake / session check| Auth
  Chat -.->|internal ticket access / audience| Tickets
~~~

La instancia fisica de PostgreSQL puede ser compartida por costo, pero Auth y Tickets tienen esquemas/DB, credenciales y migraciones distintos. Solo el reverse proxy escucha trafico publico. El navegador no habla con NATS ni bases.

## 3. Identidad, sesiones y servicio-a-servicio

**Decision de diseño elegida por el usuario:** password con bcrypt, sesiones opacas; NO JWT para sesiones del navegador.

1. Auth genera un token con CSPRNG de al menos 32 bytes, lo entrega solo en cookie **HttpOnly, Secure, SameSite=Lax, Path=/** (nombre recomendado: __Host-fixit_session bajo HTTPS). En PG persiste **hash del token**, userId, createdAt, expiresAt, revokedAt y ultimo uso; nunca el token plano.
2. Cada login emite nuevo token; logout revoca la fila y limpia cookie. Inactividad y duracion absoluta se configuran y se prueban; valores definitivos pendientes de benchmark/revision.
3. bcrypt gestiona salt unico; cost=12 es **candidato para medir**, no valor fijado. Limitar entradas a **72 bytes UTF-8** para evitar truncado silencioso de implementaciones bcrypt. Rate limit, respuesta de login no enumerable y secretos fuera de Git. No pre-hash improvisado.
4. **Auth es autoritativo sobre identidad/rol y vigencia de sesion**. Todos los servicios validan sesion via REST interno antes de acciones protegidas; no aceptan userId ni role del body enviado por browser.
5. Endpoints /internal/v1 son inaccesibles al proxy publico y exigen credenciales **de servicio** distintas para Tickets y Chat (bearer aleatorio por servicio, minimo privilegio, secretos externos al repo). No usar cookie del usuario como credencial de servicio. En una sola red privada Docker el canal puede ser interno; si las maquinas se separan, exigir TLS interno. Rotacion de secreto por definir.
6. Para evitar que Chat invente identidades, al autorizar una operacion de chat envia el **token opaco del usuario** a Tickets en la llamada interna autenticada. Tickets lo introspecta con Auth y decide la policy. No se almacena ni loguea ese token en Tickets; no se devuelve al cliente. Chat valida Auth al establecer la conexion Socket.
7. CSRF: validar Origin/Fetch Metadata para mutaciones de cookies y usar X-CSRF-Token ligado a la sesion para REST. En Socket.io, verificar Origin en el upgrade (no confiar solo en CORS, que no protege WebSocket) y autenticar handshake; revalidar por evento, pues middleware de conexion se ejecuta una vez.

**Falla:** Auth no disponible => nuevas operaciones protegidas devuelven 503 / deny, nunca permitir por cache caducada. Sesion invalida => 401. Servicio sin credencial valida => 401/403 en la API interna.

## 4. Contrato HTTP publico propuesto (v1)

Prefijo publico /api/v1. JSON de exito: {data, requestId}; error: {error:{code,message}, requestId}. Todos los IDs son UUID; timestamps ISO 8601 UTC. No hay implementacion OpenAPI aun.

| Metodo y ruta | Actor | Entrada / salida clave | Fallos |
| --- | --- | --- | --- |
| POST /auth/login | Publico | {email,password} -> 200 {data:{user:{id,email,role}},requestId} + Set-Cookie | 401, 422, 429 |
| GET /auth/csrf | Sesion valida | -> 200 {data:{csrfToken}} | 401 |
| POST /auth/logout | Sesion o cookie previa | -> 204, revocacion y Clear-Cookie | 503 si no puede garantizar revocacion |
| GET /auth/me | Sesion valida | -> 200 {data:{id,email,role}} | 401, 503 |
| POST /tickets | Reporter | {title,description,category,priority?} -> 201 {data:{id,status:OPEN,version:1}} | 401, 403, 422 |
| GET /tickets | Segun scope | ?scope=mine/assigned/available/all&status=... -> lista filtrada en backend | 401, 403 |
| GET /tickets/:id | Dueño/agente actual/admin | -> ticket completo, version, assigneeId | 401, 404 |
| POST /tickets/:id/claim | Support Agent | -> 200 {data:{id,status:ASSIGNED,assigneeId,version}} | 403/404, 409 |
| PATCH /tickets/:id/status | Actor autorizado | {to,expectedVersion,reason?} -> ticket actualizado | 403/404, 409, 422 |
| PATCH /tickets/:id/assignee | Admin | {assigneeId,expectedVersion,reason} -> ticket reasignado | 403/404, 409, 422 |
| GET /tickets/:id/events | Dueño/agente actual/admin | -> timeline ordenado, paginado | 401, 404 |
| GET /tickets/:id/messages | Dueño/agente actual/admin | ?cursor&limit (default 50, max definido) -> mensajes paginados | 401, 404, 503 |
| GET /health | Infra | -> liveness sin secretos; readiness por servicio, interno | 503 si no listo |

El scope **available** solo expone resumen limitado de tickets OPEN sin asignar, nunca mensajes ni descripcion sensible. No se acepta userId ni ownerId desde el cliente. Cualquier agent/admin que cree tickets como reporter queda como opcion fuera del recorrido esencial hasta confirmar FR-003/tabla de 002.

**Semantica de errores:** 401 sesion no valida, 403 actor autenticado sin capacidad global, 404 ticket inexistente o no revelable, 409 version/estado/claim en conflicto, 422 input invalido, 429 rate limit, 503 dependencia requerida indisponible. GET no debe filtrar existencia entre tickets de otros usuarios.

## 5. Contratos REST internos (NO exponer al navegador)

| Emisor -> receptor | Endpoint | Peticion | Resultado |
| --- | --- | --- | --- |
| Tickets/Chat -> Auth | POST /internal/v1/sessions/introspect | {sessionToken} + Authorization: Bearer servicio | {active:true,subject:{userId,role},expiresAt} o {active:false} |
| Chat -> Tickets | POST /internal/v1/tickets/:id/authorize | {sessionToken,action:chat.read/chat.write/chat.subscribe} + bearer de Chat | {allowed,actorId,ticketVersion,ticketStatus,code?}; Tickets consulta Auth |
| Chat -> Tickets | GET /internal/v1/tickets/:id/chat-audience | Bearer de Chat | {reporterId,assigneeId,status,version}; sin cuerpos de mensajes |

Solo Auth emite roles de usuario; Tickets puede decidir **ownership y estado del ticket**. Chat no infiere permisos de un evento JetStream ni de una sala Socket.io. Las respuestas de introspeccion no se cachean en G1; medir latencia en G2 y revisar si se requiere una ventana de cache con invalidacion real.

**Contrato del fallo:** credenciales de servicio invalidas -> 401/403; sesion del usuario invalida -> active:false / allowed:false; dependencia Auth/Tickets no accesible -> 503 y fail-closed. **Nunca convertir timeout a allowed:true.**

## 6. RBAC + ownership (autoridad = Tickets)

| Accion | Reporter | Support Agent | Admin |
| --- | --- | --- | --- |
| Crear ticket IT | Si | No necesario en MVP | No necesario en MVP |
| Listar tickets | Propios | Asignados + cola resumida | Todos |
| Leer ticket completo y timeline | Propios | Solo asignados actualmente | Todos |
| Claim OPEN sin asignado | No | Si, atomico | No necesario en MVP |
| ASSIGNED -> IN_PROGRESS | No | Solo asignado | Excepcion auditada |
| IN_PROGRESS -> RESOLVED | No | Solo asignado | Excepcion auditada |
| RESOLVED -> CLOSED | Solo dueño | No | Con motivo auditado |
| OPEN -> CANCELLED | Solo dueño, sin agente | No | Con motivo auditado |
| Reasignar | No | No | Si, motivo obligatorio |
| Leer historico de mensajes | Propios | Solo asignado actual | Todos |
| Enviar mensaje / join | Propio y ticket asignado activo | Asignado actual y activo | Ticket activo |
| Administrar cuentas/roles | No | No | Politica exacta pendiente con Auth |

**Activo para escritura:** ASSIGNED o IN_PROGRESS; OPEN no tiene chat, y RESOLVED / CLOSED / CANCELLED son solo lectura. Los mensajes no se borran al cambiar asignacion. Un agente anterior no conserva acceso al historial ni al stream privado tras reasignacion. El reporter conserva lectura de su propio caso cerrado.

**Version:** cada mutacion valida expectedVersion y actualiza version. Claim protege status+assignee en DB independientemente del cliente. Un 409 no genera evento ni auditoria de exito. Las comprobaciones de ownership son backend, nunca flags de React.

## 7. Contrato Socket.io / Chat

**Handshake:** cookie del mismo origen, Origin permitido, Auth introspection. Socket.io middleware solo autentica la conexion; **cada** ticket:join y chat:send revalida autorizacion contra Tickets (que consulta Auth).

| Evento cliente | Payload | ACK |
| --- | --- | --- |
| ticket:join | {ticketId} | {ok:true,data:{ticketId,version}} o {ok:false,error:{code,message}} |
| ticket:leave | {ticketId} | {ok:true} |
| chat:send | {ticketId,clientMessageId,body} | {ok:true,data:{messageId,ticketId,senderId,createdAt,clientMessageId}} o error |

Servidor -> cliente: **chat:message** con los campos de mensaje, **ticket:updated** solo como señal de refresco (no sustituye GET al servicio dueño). Body de mensaje no mayor a 2 KiB por propuesta y validacion contra spam; el senderId procede de Auth, no del socket payload.

Mongo inserta antes del ACK; indice unico (ticketId,senderId,clientMessageId) permite devolver el mismo ACK en reintentos sin duplicar mensaje ni broadcast. Mongo caido => ACK de error, sin emision de exito. Tras reconexion el cliente lee historial HTTP con cursor estable (createdAt + id).

**Reasignacion/revocacion:** cambios de Tickets llegan por eventos y ayudan a sacar sockets de salas, pero **el evento no autoriza**. Para cada broadcast sensible Chat solicita audiencia actual a Tickets y filtra sockets de usuarios con sesion vigente y permiso actual; un socket unido ayer no basta. Si Tickets/Auth no responden, se difiere la entrega. **Riesgo por resolver en G3:** la consulta de permiso y el commit de reasignacion pueden competir; no afirmar revocacion instantanea linealizable sin un protocolo mas fuerte. Diseñar y medir esa carrera antes de declarar cumplido FR-011.

## 8. Eventos JetStream v1 y consistencia

- Productor **solo Tickets** inicialmente. Stream propuesto: FIXIT_TICKET_EVENTS (file storage, LimitsPolicy, retencion y max bytes acotados a definir en G2); subjects: fixit.ticket.*.v1. Durable pull consumer de Chat: chat-ticket-projection-v1.
- Tipo de dominio en body: ticket.created.v1, ticket.claimed.v1, ticket.status-changed.v1, ticket.reassigned.v1. CLOSED y CANCELLED se representan con ticket.status-changed.v1; no crear eventos redundantes.
- Envelope versionado: eventId, type, schemaVersion=1, aggregateId=ticketId, aggregateVersion, occurredAt, correlationId y payload minimo. No publicar password hashes, email, descripcion ni cuerpo de chat.
- **Transactional outbox:** una transaccion de Tickets escribe aggregate + timeline + outbox. Publicador envia a JetStream, espera publish ACK y marca outbox como publicada. Falla antes de ese punto => reintento. Nats-Msg-Id=eventId facilita dedupe dentro de ventana del broker, pero NO sustituye inbox idempotente.
- Chat procesa at-least-once, registra eventId y ultimo aggregateVersion en proyeccion, ACK solo tras persistir; ante gaps o version inesperada, reconcilia con Tickets. No hay orden global, exactly-once end-to-end ni atomicidad entre PostgreSQL y Mongo.
- Si JetStream cae, HTTP de Tickets continua y outbox queda pendiente. Si Chat cae, el backlog se consume al volver. Si retention agota eventos, se reconstruye la proyeccion desde Tickets.
- Las consultas/decisiones de acceso siempre van a Tickets, aunque el consumidor de eventos este retrasado.

## 9. Escenarios obligatorios antes de implementar funciones avanzadas

1. Login valido, logout, cookie caducada/revocada, cambio de rol y usuario deshabilitado; REST y socket rechazan usuario inactivo.
2. Dos agentes hacen claim simultaneo: un ganador, otro 409; solo un timeline y un outbox event.
3. Reporter A no puede consultar mensajes/ticket de Reporter B; la cola disponible no expone contenido privado.
4. Admin reasigna mientras Agent A conserva socket abierto: Agent A no puede hacer nuevos joins, GET ni sends; verificar tambien race send/reassign.
5. Enviar mismo clientMessageId dos veces devuelve mismo mensaje y una sola emision logica.
6. Mongo caido: no ACK positivo; broker caido: ticket commit y outbox persisten; Chat caido: Ticket opera.
7. Outbox reprocesada, eventos duplicados y fuera de orden: proyeccion de Chat consistente y rehidratable.
8. Origin malicioso, CSRF, servicio sin token interno y cambio de session cookie: rechazos controlados, sin secretos en logs.
9. Medir carga en host de **2 vCPU/4 GiB** con 3 runtimes Node, PostgreSQL, MongoDB, NATS y proxy antes de decidir EC2/t3.medium.

## 10. Decisiones pendientes / criterios de cierre de G1

- **G0 docente:** SE II acepta IT Help Desk y TypeScript; aclarar si dos bounded contexts **del dominio core** son obligatorios; Cloud confirma evidencias/fechas. El PDF no equivale a permiso de los profesores.
- **Producto:** confirmar politica de alta/invitacion, gestion de usuarios por Admin y si Agent/Admin pueden crear tickets de si mismos.
- **Seguridad:** definir timeout de sesion, CSRF implementation, secreto interservicios y estrategia de revocacion de sockets. Validar riesgo residual de race send/reassign.
- **Contratos:** revisar las rutas/acciones/errores y guardar OpenAPI v1 al comenzar G4; fijar exactamente payloads e indexacion/idempotencia.
- **Operacion:** retencion JetStream, backups, limites de recursos, costos AWS; no crear infraestructura hasta pasar G2/G5.
- **Ratificacion:** el equipo aprueba o rechaza [ADR-005](adr/ADR-005-three-services-opaque-sessions.md). Mientras sea proposed, no declarar G1 cerrado.
