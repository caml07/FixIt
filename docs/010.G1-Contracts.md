# 010 · G1 — Contextos, contratos y autorizacion

**Baseline Contract-First 0.2.0 congelada por el usuario el 26 nov 2026 para iniciar implementación.** Abarca OpenAPI/REST, esquema Prisma + migraciones SQL y protocolo Socket.IO de esta documentación. La baseline se registra en `dev` antes de los commits de implementación. La revisión técnica de Valeria/Rina sigue pendiente y **no se les atribuye ratificación técnica**. G1 no está PASS. El primer Chat local está en el working tree; no hay controladores de Tickets integrados. Cualquier cambio posterior requiere una nueva versión y actualización coordinada de todos los artefactos. El MVP sigue siendo **IT Help Desk**, no mantenimiento de instalaciones.

## 1. Limites y lenguaje ubicuo

| Bounded context candidato | Servicio desplegable | Tipo DDD | Modelo y autoridad | No conoce |
| --- | --- | --- | --- | --- |
| Identity & Access | Auth | Generico | Account, Session, Role; credenciales, Argon2id, revocacion, login | Tickets, mensajes |
| IT Support Ticketing | Tickets | Core | SupportTicket, Assignment, TicketStatus, TicketTimeline, categoria, claim y policy de acceso por ticket | Password hashes, cuerpos de mensajes |
| Ticket Conversation | Chat | Supporting | Message, clientMessageId, historial, conexion Socket.io, entrega realtime | Estado autoritativo del ticket, roles globales |

**Un servicio no es automaticamente un bounded context.** Esta correspondencia es una propuesta deliberada de limites de modelo, no una inferencia por contenedores. Auth expone una identidad estable (userId y role); Tickets la traduce a Reporter / AssignedAgent / Admin para decisiones propias. Chat usa ticketId y senderId como referencias, sin compartir entidades ORM ni tablas.

**Restriccion COP3851:** la [especificacion Contract-First](references/COP3851_Capstone_2026-11-11.md) exige OpenAPI y esquema 3NF con FK y migraciones en un commit **anterior a los controllers generados por IA**. El usuario congeló la baseline 0.2.0 para implementación el 26 nov y el commit de la baseline queda registrado en `dev`. No generar controladores en `dev`; las ramas de implementación deben conservar esta baseline como ancestro.

**Decision posterior del usuario (11 nov, direccion G1):** se eligio **una sola database PostgreSQL con dos esquemas `auth` y `tickets`**, conservando tres runtimes Express separados (Auth, Tickets y Chat). En esta topologia **si** pueden existir FK SQL entre `tickets.*` y `auth.users(id)`. Los permisos SQL siguen separados por servicio: las FK no autorizan a Tickets a leer el password hash ni las sesiones de Auth. Requiere migraciones coordinadas, cuentas DB de minimo privilegio y revision del equipo; [ADR-005](adr/ADR-005-three-services-opaque-sessions.md) continua propuesto. MongoDB sigue reservado para Chat.

**Terminologia del producto:** Reporter crea **SupportTicket**; Support Agent reclama uno sin asignar; Admin puede reasignar. No se usan WorkOrder, DISPATCHED, HazardPolicy, SLA ni AI triage del PDF adicional.

**Ajuste de MVP del 11 nov (actualizado por usuario el 26 nov; equipo pendiente):**
evidencia opcional multiarchivo, edicion basica del ticket propio mientras
`OPEN`, el flujo de estados ya definido y **notificaciones in-app** de
creacion (Admin), asignacion, reasignacion, cambio de estado y mensaje nuevo
(destinatarios permitidos). El upload pertenece a Tickets, no a Auth ni al
token. Limites aprobados: hasta 5 archivos/2 videos, imagen JPEG/PNG/WebP
5 MiB, MP4 25 MiB y 50 MiB combinados por ticket. Formato real, permisos,
cuota y descarga privada quedan sujetos a pruebas al implementar.
Storage seleccionado: filesystem privado local y S3 privado cuando Cloud
este autorizado; no agregar MinIO obligatorio ni servicio de archivos.
Notificaciones:
eventos de Tickets por outbox/JetStream hacia Chat, Socket.IO para avisos,
historial del ticket/Chat para recuperar el estado cuando se reconecte;
no construir sistema independiente de inbox, push o correo en MVP.

**Mapa de contextos (upstream -> downstream):**

~~~mermaid
flowchart LR
  Identity[Identity & Access<br/>generic] -->|Open Host Service: session introspection| Ticketing[IT Support Ticketing<br/>core]
  Identity -->|Open Host Service: session introspection| Conversation[Ticket Conversation<br/>supporting]
  Ticketing -->|Customer-Supplier: access policy API| Conversation
  Ticketing -->|Published Language: ticket events v1| Conversation
~~~

Los consumidores usan IDs y contratos publicos versionados, no el modelo ORM de otro contexto. El contrato de audiencia y acceso de Tickets es sincrono porque la autorizacion **no puede depender del retraso de la proyeccion de eventos**.

**Modelo DDD dentro de Tickets (MVP):**
- SupportTicket es aggregate root y protege OPEN -> ASSIGNED -> IN_PROGRESS -> RESOLVED -> CLOSED; OPEN -> CANCELLED. Reasignar no cambia status.
- La asignacion y categoria pertenecen al dominio Tickets; TicketTimeline es append-only. Un cambio de estado escribe ticket, auditoria y outbox **en una transaccion PostgreSQL**. **La baseline 0.2.0 ya contiene `reporterUrgency` y `effectivePriority`**, con la separación de autoridad descrita en FR-020 y B3; no implementar un segundo campo ni derivar la prioridad desde la urgencia.
- El claim usa UPDATE condicionado por status=OPEN y assigneeId IS NULL; no requiere leer y despues actualizar sin proteccion. Dos agentes compiten: exactamente un 200 y otro 409 en el test previsto.
- Ticket referencia `auth.users(id)` mediante FK SQL **entre esquemas de la misma base PostgreSQL**; los servicios mantienen autorizacion y roles SQL independientes. La FK comprueba existencia, **no comprueba que un ID sea REPORTER/AGENT**, ni sustituye el permiso por recurso de Tickets.

### ORM recomendado para este diseño (12 nov; propuesta, no implementado)

**PostgreSQL: Prisma ORM + Prisma Migrate**, para Auth y Tickets. Prisma
admite **varios esquemas PostgreSQL** en un datasource y permite asociar
modelos con `@@schema("auth")` / `@@schema("tickets")`, así como
relaciones FK entre los dos esquemas; comprobar la API de la versión de
Prisma que finalmente se fije. **Ya existe un
[schema.prisma de diseño](database/schema.prisma) y una
[migracion SQL inicial con Prisma Migrate](database/migrations/20261115000100_initial/migration.sql)**.
No hay version de Prisma instalada/fijada ni migracion generada por Prisma.

**Advertencia de ownership:** al compartir una sola base y tener FK
cruzadas, **no ejecutar dos migradores Prisma autónomos** (uno en cada
microservicio). Recomendar **un único owner/pipeline de migraciones**
que conoce ambos esquemas, revisa el SQL, mantiene el orden de FK y
commitea una historia coherente. Los servicios pueden mantener clientes
Prisma y credenciales PostgreSQL **separados** para el runtime: Auth
opera sus tablas; Tickets opera las suyas y comprueba roles/identidad
mediante REST. La capacidad de Prisma para expresar una FK no concede
permiso para consultar directamente los hashes de Auth desde Tickets.
Definir credenciales de migración distintas de las de aplicación.

**Chat: MongoDB + Mongoose**. Colección conceptual `messages` con
`ticketId`, `senderId`, `clientMessageId`, `body`, `createdAt`;
índices por `(ticketId, createdAt, _id)` para historial y
`UNIQUE(ticketId, senderId, clientMessageId)` para deduplicar reintentos.
Colección de deduplicación de eventos `processed_events` / inbox
para `eventId` de JetStream si se utiliza proyección persistente;
el cambio de inbox y proyección debe ser consistente antes del ACK.
**El `ticketId` en Mongo es referencia lógica, no FK PostgreSQL**;
Chat pide permisos vigentes a Tickets. No mover el historial crítico
del ticket desde PostgreSQL a Mongo por inercia.

**Fotografías:** la tabla relacional de metadata no equivale a almacenar
el archivo en PostgreSQL; mantener objeto privado y descarga autorizada.
No decidir aún volumen protegido frente a S3 privado, ni mezclar estas
fotos con el bucket académico de artefactos.

**Fuentes técnicas:** [Prisma multi-schema](https://docs.prisma.io/docs/orm/prisma-schema/data-model/multi-schema),
[Prisma Migrate](https://www.prisma.io/docs/orm/v7/prisma-migrate),
[Mongoose Schemas](https://mongoosejs.com/docs/guide.html).
**Estado:** recomendación compatible con el diseño, pendiente revisión
de Valeria/Rina y fase Contract-First; **no crea otro gate**.

**Orden conceptual futuro:** definir primero los usuarios de Auth; despues
categorias, tickets, timeline y outbox, junto a sus FK entre esquemas.
Auth y Tickets conservaran identidades y permisos SQL separados, sin lectura
cruzada de datos privados. **La migracion SQL se aplico solo a una PostgreSQL
17 temporal para probar el DDL**; no hay tablas persistentes, cuentas de
servicio ni pruebas del producto. Ver [evidencia](database/README.md).

## 3. Identidad, sesiones y servicio-a-servicio

**Decision de diseño del usuario (15 nov):** Argon2id para las contrasenas, sesiones opacas para el navegador; NO JWT.

**Baseline de producto confirmado (10-11 nov; aclaracion 16 nov):** en el **MVP** la cuenta identifica a una **persona**, no a la computadora o al salon; docentes pueden iniciar sesion desde distintas computadoras. La deteccion automatica de la computadora de origen, una identidad fija por equipo/kiosco o un inventario por etiqueta/QR/MAC son ideas para **despues del MVP**, no contratos presentes. Un navegador web convencional no obtiene de forma fiable la MAC local; nunca utilizar MAC como autentificacion. Solo **Admin** puede dar de alta y gestionar cuentas; el registro publico queda excluido. Admin crea una **contrasena temporal aleatoria**, que el usuario **debe cambiar en el primer acceso**. El **primer Admin se provisionara mediante un seeder de base de datos**, con un secreto aleatorio no versionado. Las credenciales temporales caducan tras **72 horas**; son decisiones de diseno del usuario, no plazos prescritos por NIST. El piloto se limita a **docentes, personal autorizado y usuarios ficticios de prueba**. FixIt cubre **soporte IT general**; salon y equipo son opcionales en el ticket y nunca sustituyen la identidad. No se usara una MAC como prueba de autenticacion. El canal exacto de entrega segura y los detalles del seeder se revisaran antes de implementarlos. **Estas decisiones de producto NO ratifican ADR-005.**

**Invariante propuesta para activacion (requiere verificacion):** cuenta creada como `PENDING_PASSWORD_CHANGE` con password temporal almacenada solo en forma de hash; tras autenticarse solo se permiten logout y cambio inicial de password (ademas de endpoints tecnicos minimos), nunca tickets/chat. Cambiar password invalida la credencial temporal, revoca sesiones anteriores y marca cuenta activa; Admin puede forzar restablecimiento, registrar quien lo solicito y revocar sesiones. El password temporal no debe persistirse en claro, reaparecer en UI, quedar en logs ni incluirse en datos de prueba desplegados. No asumir entrega segura por correo ni contrasena inicial fija.

1. Auth genera un token con CSPRNG de al menos 32 bytes, lo entrega solo en cookie **HttpOnly, Secure, SameSite=Strict, Path=/** (exigencia COP3851; nombre recomendado: __Host-fixit_session bajo HTTPS). En PG **se propone** persistir hash del token, userId, createdAt, expiresAt, revokedAt y ultimo uso; nunca el token plano.
2. Cada login emite nuevo token; logout revoca la fila y limpia cookie. Inactividad y duracion absoluta se configuran y se prueban; valores definitivos pendientes de benchmark/revision.
3. **NIST SP 800-63B-4:** para password como factor unico, minimo **15 caracteres**, admitir **al menos 64**, aceptar espacios y Unicode (normalizacion NFC consistente antes del hash y verificacion), sin reglas arbitrarias de composicion ni rotacion periodica obligatoria; bloquear contrasenas comprometidas y limitar intentos. **Argon2id** elegido el 15 nov; como punto de partida de benchmark usar `m=19456 KiB, t=2, p=1` segun OWASP, con salt por password manejado por la libreria y hash codificado con parametros. Medir costo de RAM/CPU y concurrencia en instancia candidata, sin bajar de una configuracion OWASP equivalente por conveniencia. Bcrypt queda solo como antecedente academico. Fuentes: [NIST 800-63B-4 §3.1.1](https://pages.nist.gov/800-63-4/sp800-63b.html#passwords) y [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
4. **Auth es autoritativo sobre identidad/rol y vigencia de sesion**. Todos los servicios validan sesion via REST interno antes de acciones protegidas; no aceptan userId ni role del body enviado por browser.
5. Endpoints /internal/v1 son inaccesibles al proxy publico y exigen credenciales **de servicio** distintas para Tickets y Chat (bearer aleatorio por servicio, minimo privilegio, secretos externos al repo). No usar cookie del usuario como credencial de servicio. En una sola red privada Docker el canal puede ser interno; si las maquinas se separan, exigir TLS interno. Rotacion de secreto por definir.
6. Para evitar que Chat invente identidades, al autorizar una operacion de chat envia el **token opaco del usuario** a Tickets en la llamada interna autenticada. Tickets lo introspecta con Auth y decide la policy. No se almacena ni loguea ese token en Tickets; no se devuelve al cliente. Chat valida Auth al establecer la conexion Socket.
7. CSRF: validar Origin/Fetch Metadata para mutaciones de cookies y usar X-CSRF-Token ligado a la sesion para REST. En Socket.io, verificar Origin en el upgrade (no confiar solo en CORS, que no protege WebSocket) y autenticar handshake; revalidar por evento, pues middleware de conexion se ejecuta una vez.

**Falla:** Auth no disponible => nuevas operaciones protegidas devuelven 503 / deny, nunca permitir por cache caducada. Sesion invalida => 401. Servicio sin credencial valida => 401/403 en la API interna.

**Nota oral del usuario, sin confirmar (11 nov):** Mr. Felix habria mencionado almacenar informacion de sesiones/tokens en **MongoDB con Mongoose** y conservar documentos marcados `deprecated` en vez de eliminarlos o revocarlos. **No aparece en el PDF recibido**, que permite sesiones o JWT y exige cookies seguras. Antes de mover el store de Auth, confirmar si se referia a **soft-delete / registro historico**: una sesion etiquetada como obsoleta debe **dejar de autorizar solicitudes inmediatamente** cuando vence o hay logout, aunque su documento permanezca para auditoria. No interpretar `deprecated` como `active`. MongoDB TTL elimina de forma asincrona y **no sustituye** la comprobacion `status/expiresAt` del lado servidor. Mantener **PostgreSQL como propuesta actual**, no como requisito inmutable. Fuentes: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [MongoDB TTL](https://www.mongodb.com/docs/manual/core/index-ttl/).

La ruta publica `GET /tickets/:id/messages` corresponde a **Chat**, no a Tickets, desde el proxy; Chat debe pedir autorizacion vigente a Tickets y no consultar PostgreSQL. Ninguno de estos diseños implica un controlador desplegado. Ver [Gates](011.Gates.md).

### B3 — Formulario de ticket y evidencia (defaults aprobados por usuario, 26 nov; incluidos en baseline congelada 0.2.0)

**Alcance:** se conserva el IT Help Desk y el formulario ya revisado con Rina. El usuario aprobó las escalas y límites siguientes el 26 nov. Esta aprobación del usuario autoriza preparar el contrato, pero **no se atribuye como ratificación técnica de Valeria/Rina**. La IA de triage permanece fuera del MVP.

| Campo | Contrato seleccionado |
| --- | --- |
| Hora | `createdAt` UTC generado por servidor. No se acepta hora enviada por el navegador ni se agrega una segunda hora del incidente. |
| Subject / title | `title` continúa obligatorio (1–160 caracteres), según el formulario UI aprobado; no se genera automáticamente. |
| Tag / Category | Código del catálogo IT existente (`NETWORK`, `HARDWARE`, `SOFTWARE`, `ACCOUNTS`, `PERIPHERALS`). No crear tags libres ni categoría de instalaciones. |
| Description | Texto requerido, 1–5000 caracteres. |
| Urgencia Reporter | Obligatoria: `LOW`, `NORMAL`, `HIGH`. El Reporter puede cambiarla mientras el ticket siga `OPEN`; no concede autoridad sobre la prioridad oficial. |
| Prioridad oficial | Inicia `null`; valores `P1_CRITICAL`, `P2_HIGH`, `P3_NORMAL`, `P4_LOW`. Solo Support Agent **asignado** o Admin puede fijarla/modificarla mediante `PATCH /priority` con `expectedVersion`. Un motivo es obligatorio si ya existía una prioridad. **Reglas de persistencia y autorización:**

- `reporter_urgency` es NOT NULL; los tickets anteriores al delta reciben `NORMAL` como valor neutral. `effective_priority` admite NULL hasta triage; tickets legacy que ya estaban `IN_PROGRESS`, `RESOLVED` o `CLOSED` reciben `P3_NORMAL` para cumplir la invariante sin inventar una migración de estado.
- La edición de urgencia queda dentro del `PATCH /tickets/{ticketId}` existente y solo aplica al Reporter propietario mientras `OPEN`.

- `IN_PROGRESS` requiere `effective_priority` no nula. PostgreSQL mantiene un `CHECK` para esta invariante, además de la validación de transición en Tickets.
- Los adjuntos se suben individualmente a `POST /tickets/{ticketId}/attachments`, solo por el Reporter propietario mientras `OPEN`, con `expectedVersion`. El detalle del ticket devuelve metadata; `GET /tickets/{ticketId}/attachments/{attachmentId}` transmite el archivo solo después de autorizar el ticket. No hay URL pública ni endpoint de borrado en el MVP.

### B2 — Semantica de reasignacion y envios (alternativa A seleccionada por usuario; review equipo pendiente)

**Alternativa A seleccionada por el usuario el 11 nov 2026; ratificacion de equipo pendiente:** toda **nueva** operacion de un agente anterior iniciada una vez confirmada la reasignacion se rechaza (GET, join, send, recipients). Para `chat:send` Chat comprueba sesion FULL y permiso vigente en Tickets justo antes de insertar en Mongo; un permiso concedido antes del commit de reasignacion **puede** quedar en vuelo y persistir despues. Esto constituye un solapamiento de operaciones, no una garantia linealizable de revocacion. El cliente puede mostrar error/conflicto o ACK de un mensaje cuyo procesamiento ya habia comenzado, segun el orden real; la semantica y pruebas deben preservar esa distincion.

Cada reintento debe verificar primero la sesion y autorizacion actual, antes de devolver ACK/datos de un mensaje previo. JetStream avisa cambios de asignacion pero no concede permisos. Un evento retrasado no sustituye las consultas sincronas. El mensaje persistido sigue en el historial para quienes conservan acceso.

**Alternativa estricta, NO recomendada sin requisito expreso:** hacer la aceptacion de mensajes y la reasignacion mutuamente serializables mediante coordinacion con Tickets, incluyendo recuperacion ante timeout Mongo/PG. Una validacion repetida de version o un token de autorizacion **no elimina por si solo** la carrera entre la validacion en PG y la escritura en Mongo. Seria una ampliacion importante del protocolo, no un ajuste de flag.

**Prueba G3 sugerida:** intercalar deliberadamente un `chat:send` autorizado, pausa antes del insert, y `PATCH /assignee`; registrar respuesta y mensaje segun la semantica MVP elegida. Tras el commit, los nuevos GET/join/send del agente viejo fallan; la audiencia de futuros broadcasts excluye al revocado. El agente nuevo puede recuperar historial. Repetir con Auth/Tickets caidos, mensaje duplicado y ACK perdido. No afirmar esta propiedad sin test de integracion.

**Semantica de errores:** 401 sesion no valida, 403 actor autenticado sin capacidad global, 404 ticket inexistente o no revelable, 409 version/estado/claim en conflicto, 422 input invalido, 429 rate limit, 503 dependencia requerida indisponible. GET no debe filtrar existencia entre tickets de otros usuarios.

RESOLVED / CLOSED / CANCELLED permiten historial y suscripcion de solo lectura con permiso vigente. Los mensajes no se borran al cambiar asignacion. Un agente anterior no conserva acceso al historial ni al stream privado tras reasignacion. El reporter conserva lectura de su propio caso cerrado.

**Version:** cada mutacion **salvo claim** valida `expectedVersion` y actualiza version: la creación inicia en `version=1`, el claim toma solo `OPEN` sin asignado con un `UPDATE ... RETURNING` condicional e incrementa versión, sin campo de version del cliente. Un segundo claim devuelve 409. La edición `PATCH /tickets/:id` exige `expectedVersion` **más al menos uno** de `title`, `description` o `category`; un cuerpo con solo `expectedVersion` recibe 422, no incrementa versión ni produce timeline. El reporter solo edita su `OPEN` propio. `PATCH /status` aplica únicamente las transiciones de la matriz; Admin aporta `reason` no vacío cuando interviene por excepción. Un 409/422 no genera evento ni auditoría de éxito. Las comprobaciones de ownership son backend, nunca flags de React.

## 7. Contrato Socket.io / Chat

**Paquete aprobado por el usuario el 20 nov 2026:** las precisiones de esta seccion afectan G1 y sus pruebas G3, sin crear gates ni declararlos PASS. La baseline 0.2.0 quedó commiteada en `dev`; el primer Chat local en `feat/chat` usa simuladores de Auth/Tickets y Mongo local. Aún falta integrar Auth/Tickets reales y completar JetStream. Esta evidencia no sustituye las pruebas con servicios reales ni la revisión técnica del equipo. Fotos/video siguen perteneciendo al ticket, no al mensaje.

**Handshake:** cookie del mismo origen, Origin permitido, Auth introspection. Socket.io middleware solo autentica la conexion; **cada** ticket:join y chat:send revalida autorizacion contra Tickets (que consulta Auth).

| Evento cliente | Payload | ACK |
| --- | --- | --- |
| ticket:join | {ticketId} | {ok:true,data:{ticketId,version}} o {ok:false,error:{code,message}} |
| ticket:leave | {ticketId} | {ok:true} |
| chat:send | {ticketId,clientMessageId,body} | {ok:true,data:{messageId,ticketId,senderId,createdAt,clientMessageId}} o error |

Servidor -> cliente: **chat:message** con el objeto `Message` de OpenAPI (`id`, `ticketId`, `senderId`, `clientMessageId`, `body`, `createdAt`); `messageId` del ACK representa el mismo UUID que `Message.id`. **ticket:updated** solo es señal de refresco (no sustituye GET al servicio dueño).

**Validacion de envio:** `ticketId` y `clientMessageId` son UUID; `body` es texto plano, no vacio al comprobar espacios y de maximo **2.048 bytes UTF-8**, no 2.048 caracteres. Conservar el texto valido tal como se recibio; la comprobacion de espacios no lo transforma. Rechazar campos extra, incluidos `senderId` y `role`; el emisor procede de la identidad verificada por Auth/Tickets. El cliente presenta el texto sin interpretarlo como HTML.

**Idempotencia y ACK:** Mongo inserta antes del ACK; indice unico `(ticketId,senderId,clientMessageId)`. Cada intento verifica sesion y permiso actuales **antes** de devolver un resultado previo. Misma clave y mismo texto exacto devuelve el ACK original, sin nueva escritura ni broadcast deliberado por el reintento. Misma clave con otro texto produce conflicto, sin sobrescribir. Mongo caido o persistencia no confirmada => ACK de error, sin emision de exito; un timeout puede dejar resultado incierto y se resuelve reintentando la misma clave tras reautorizar. No prometer entrega exactamente una vez: la garantia es una sola persistencia por clave, cliente que deduplica por `Message.id` e historial recuperable.

**Historial:** `GET /api/v1/tickets/{ticketId}/messages` sin cursor devuelve los ultimos mensajes (default 50, maximo 100). Cada pagina viene en orden ascendente por `(createdAt,id)`; `nextCursor` permite cargar mensajes estrictamente anteriores al mas antiguo de la pagina, sin solapamiento, y es `null` cuando no quedan anteriores. El cursor es opaco y no concede permisos. Validar UUID, cursor y limite; entrada invalida => 422. Tras reconexion, reautenticar, verificar permiso, consultar desde la pagina mas reciente y cargar anteriores hasta cubrir el intervalo perdido, deduplicando por ID; no usar el cursor de paginas antiguas como cursor de novedades.

**Estados y suscripcion:** `ticket:join` autoriza `chat.subscribe` con sesion vigente. OPEN no admite sala ni envio; su GET devuelve historial vacio solo a actores autorizados. ASSIGNED/IN_PROGRESS admiten lectura, suscripcion y escritura. RESOLVED/CLOSED/CANCELLED admiten lectura y suscripcion, pero no nuevos envios; una operacion ya autorizada en vuelo puede terminar y notificarse a destinatarios que conserven permiso. El cambio a solo lectura no convierte al agente anterior en destinatario autorizado.

**Errores:** conservar el envelope de ACK `{ok:false,error:{code,message}}`. Defaults aprobados por el usuario para implementacion local el 20 nov 2026: `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `CONFLICT` (409, estado incompatible o clave reutilizada con otro texto), `VALIDATION_ERROR` (422), `RATE_LIMITED` (429) y `DEPENDENCY_UNAVAILABLE` (503). Estos numeros expresan correspondencia HTTP, no estados HTTP del transporte Socket.IO. Nunca incluir errores de drivers, tokens ni cuerpos de mensajes en respuestas o logs.

**Limites iniciales aprobados para pruebas locales:** 30 intentos de envio por minuto por usuario; 120 lecturas o joins por minuto por usuario en un contador compartido HTTP/Socket.IO. Compartir contadores entre sesiones y sockets del mismo usuario, no usar identidad enviada por cliente. Ventanas de 60 segundos; son valores configurables, no capacidad medida. Timeout de llamadas internas Auth/Tickets: 3 segundos, con fallo cerrado. MVP local de un proceso Chat: los contadores en memoria se reinician con el proceso; antes de replicas o exposicion publica revisar limitador compartido y pruebas de bypass. La retencion y reintentos de JetStream siguen pendientes para su fase de integracion.

**Reasignacion/revocacion:** cambios de Tickets llegan por eventos y ayudan a sacar sockets de salas, pero **el evento no autoriza**. Para cada broadcast sensible Chat solicita audiencia actual a Tickets y filtra sockets de usuarios con sesion vigente y permiso actual; un socket unido ayer no basta. Si Tickets/Auth no responden, se difiere la entrega. **Riesgo por resolver en G3:** la consulta de permiso y el commit de reasignacion pueden competir; no afirmar revocacion instantanea linealizable sin un protocolo mas fuerte. Diseñar y medir esa carrera antes de declarar cumplido FR-011.

## 8. Eventos JetStream v1 y consistencia

- Productor **solo Tickets** inicialmente. Stream propuesto: FIXIT_TICKET_EVENTS (file storage, LimitsPolicy, retencion y max bytes acotados a definir en G2); subjects: fixit.ticket.*.v1. Durable pull consumer de Chat: chat-ticket-projection-v1.
- Tipo de dominio en body: ticket.created.v1, ticket.claimed.v1, ticket.status-changed.v1, ticket.reassigned.v1. CLOSED y CANCELLED se representan con ticket.status-changed.v1; no crear eventos redundantes.
- Envelope versionado: eventId, type, schemaVersion=1, aggregateId=ticketId, aggregateVersion, occurredAt, correlationId y payload minimo. No publicar password hashes, email, descripcion ni cuerpo de chat.
- **Transactional outbox:** una transaccion de Tickets escribe aggregate + timeline + outbox. Publicador envia a JetStream, espera publish ACK y marca outbox como publicada. Falla antes de ese punto => reintento. Nats-Msg-Id=eventId facilita dedupe dentro de ventana del broker, pero NO sustituye inbox idempotente.
- Chat procesa at-least-once, registra eventId y ultimo aggregateVersion en proyeccion, ACK solo tras persistir; ante gaps o version inesperada, reconcilia con Tickets. No hay orden global, exactly-once end-to-end ni atomicidad entre PostgreSQL y Mongo.
- Si JetStream cae, HTTP de Tickets continua y outbox queda pendiente. Si Chat cae, el backlog se consume al volver. Si retention agota eventos, se reconstruye la proyeccion desde Tickets mediante `GET /internal/v1/tickets/chat-snapshot` paginado; `GET /internal/v1/tickets/:id/chat-audience` solo basta cuando Chat **ya conoce** el ticketId.
- Las consultas/decisiones de acceso siempre van a Tickets, aunque el consumidor de eventos este retrasado.

### Recuperacion de fallos y entrega (G1-C, opcion A seleccionada por usuario)

**Decision de diseño del usuario (11 nov, opcion A):** una caida de **NATS o Chat no debe bloquear
la creacion, claim ni transiciones de tickets** si Auth, Tickets y PostgreSQL
siguen operativos. El cambio del ticket y su registro de outbox se confirman
en **una transaccion PostgreSQL**; NATS se publica despues. No confundir
"ticket guardado" con "evento ya recibido por Chat". Una caida de
Auth o PostgreSQL puede impedir nuevas operaciones seguras: no prometer
disponibilidad total del producto. La prioridad declarada es **minimizar
acoplamiento sincrono, latencia y complejidad del camino critico**, sin
eliminar los mecanismos necesarios de seguridad e idempotencia.

~~~mermaid
flowchart TD
  Change[Comando autorizado en Tickets] --> Tx[Transaccion PostgreSQL]
  Tx -->|Commit: ticket + timeline + outbox| Saved[Ticket confirmado]
  Saved --> Publish[Publicador lee outbox pendiente]
  Publish --> Nats{NATS disponible?}
  Nats -->|No| Pending[Conservar outbox y reintentar]
  Pending --> Publish
  Nats -->|Si| Ack[Esperar publish ACK de JetStream]
  Ack --> Mark[Marcar outbox como publicada]
  Ack --> Consume[Chat: consumidor durable]
  Consume --> Check{eventId ya procesado?}
  Check -->|Si| Confirm[ACK del consumidor, sin repetir efectos]
  Check -->|No| Version{aggregateVersion esperada?}
  Version -->|Si| Persist[Guardar inbox y proyeccion de forma atomica]
  Persist --> Confirm
  Version -->|No| Reconcile[Reconciliar desde Tickets; no dar permisos por evento]
  Reconcile --> Persist
~~~

**Caso de ACK perdido:** si JetStream persiste un evento pero el publicador
no recibe su ACK, la outbox puede reintentar el mismo `eventId`. El
`Nats-Msg-Id` ayuda a deduplicar publicaciones **dentro de la ventana del
broker**; el consumidor **tambien** debe mantener inbox idempotente. La
marca de outbox `published` solo se guarda despues de recibir el ACK.

**Caso de ACK de consumidor perdido:** Chat guarda el resultado de procesar
un evento y el `eventId` juntos en Mongo, **antes** de confirmar consumo
a JetStream. Si NATS reentrega, el identificador ya procesado evita volver
a aplicar el cambio. Solo devolver ACK tras persistencia; un error
transitorio conserva posibilidad de reintento. El manejo de fallos
permanentes y la politica de mensajes que agotan reintentos quedan por
dimensionar al implementar; no permitir un bucle de consumo silencioso
e ilimitado.

**Recuperacion tras perdida del stream (G1, propuesta minima):** iniciar o recrear el stream y el consumidor durable **antes** de enumerar el estado autoritativo. Chat llama `GET /internal/v1/tickets/chat-snapshot` (solo red interna y bearer Chat), pagina por UUID ascendente con cursor opaco y `limit <= 100`, y persiste en Mongo `ticketId`, audiencia, estado y version sin secretos. Los eventos que llegan durante el barrido permanecen retenidos en JetStream; al aplicarlos, **nunca retroceder** una version y reconsultar Tickets ante huecos. La paginacion no promete un snapshot global atomico; una cuenta desactivada o una reasignacion reciente siguen requiriendo **autorizacion sincronica**. Este proceso reconstruye el **estado presente**, no las notificaciones historicas de Socket.IO ni un log completo de eventos perdidos. Fallo de pagina/503: detener reconciliacion y reintentar, sin conceder permisos por proyeccion. No crear tabla de historial duplicada ni nuevo servicio.

**Orden de eventos:** usar `aggregateVersion` **por ticket**, no un orden
global. Un evento igual o anterior a la version aplicada no retrocede la
proyeccion; una version adelantada obliga a recuperar el estado autoritativo
en Tickets antes de actualizarla. Si el evento necesario ya salio de la
retencion, reconciliar mediante API interna autorizada o snapshot, no
inventar el estado. **La proyeccion no concede accesos**: cada operacion de
Chat sigue validandose contra Tickets y Auth.

**Mensajes de chat son otro flujo:** un `chat:send` se acepta solo tras
persistirlo en MongoDB. El ACK al navegador puede perderse, por lo que
los reintentos usan `clientMessageId` y una clave unica para no insertar
dos mensajes. Si el socket se desconecta, al reconectar se autentica
de nuevo, se verifica permiso actual del ticket y se consulta el historial
persistido por cursor. No asumir que Socket.IO reenvia broadcasts perdidos.
La alternativa B2 ya elegida sigue vigente durante reasignaciones.

| Dependencia indisponible | Se permite | No se promete |
| --- | --- | --- |
| **NATS** | Ticket y outbox se guardan en PostgreSQL; publicacion posterior | Notificacion inmediata a Chat |
| **Chat** | Tickets sigue funcionando y JetStream mantiene eventos dentro de su retencion | Lectura/envio de chat mientras Chat esta caido |
| **MongoDB** | Tickets sigue funcionando | ACK de mensaje no persistido ni historial disponible |
| **Auth** | Servir contenido publico no sensible | Nuevas operaciones protegidas sin validar sesion |
| **Tickets** | Chat puede conservar datos ya persistidos en Mongo | Autorizacion nueva o broadcasts de mensajes privados sin permiso vigente |
| **PostgreSQL** | Respuesta explicita de indisponibilidad | Creacion o cambio de ticket sin transaccion y outbox |

**Opcion A seleccionada por el usuario:** aceptar **consistencia eventual
para eventos y notificaciones**, sin hacer que el usuario espere el ACK
de NATS antes de confirmar el ticket. La publicacion sigue el commit
de PostgreSQL. Esto **no** hace asincrona la verificacion de sesiones
o permisos, que permanece REST sincrono y fail-closed. Pendiente de
ratificacion del equipo y pruebas de recuperacion. No se fijan aun ventana de deduplicacion, retencion,
`AckWait`, `MaxDeliver`, alertas o tiempos de recuperacion: requieren
capacidad y ensayos G2/G3 sobre producto real.

Fuentes de comportamiento, no evidencia de FixIt implementado:
[NATS JetStream](https://docs.nats.io/concepts/jetstream),
[NATS consumidores durable pull](https://docs.nats.io/learn/jetstream/pull-consumers),
[Socket.IO delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/).
**Estado: opcion A elegida para diseño por usuario; NO implementado,
NO ratificado por equipo y G1 NO PASS.**

## 9. Escenarios obligatorios antes de implementar funciones avanzadas

1. Login valido, logout, cookie caducada/revocada, cambio de rol y usuario deshabilitado; REST y socket rechazan usuario inactivo.
2. Dos agentes hacen claim simultaneo: un ganador, otro 409; solo un timeline y un outbox event.
3. Reporter A no puede consultar mensajes/ticket de Reporter B; la cola disponible no expone contenido privado.
4. Admin reasigna mientras Agent A conserva socket abierto: Agent A no puede hacer nuevos joins, GET ni sends; verificar tambien race send/reassign.
5. Enviar mismo clientMessageId y texto dos veces devuelve mismo ACK y una sola persistencia; otro texto produce conflicto. Reintento tras revocacion no revela el resultado previo. Cliente deduplica por ID y recupera historial ante ACK/broadcast perdido, sin prometer entrega exactamente una vez.
6. Mongo caido: no ACK positivo; broker caido: ticket commit y outbox persisten; Chat caido: Ticket opera.
7. Outbox reprocesada, eventos duplicados y fuera de orden: proyeccion de Chat consistente y rehidratable.
8. Origin malicioso, CSRF, servicio sin token interno y cambio de session cookie: rechazos controlados, sin secretos en logs.
9. Medir carga en host de **2 vCPU/4 GiB** con 3 runtimes Node, PostgreSQL, MongoDB, NATS y proxy antes de decidir EC2/t3.medium.
